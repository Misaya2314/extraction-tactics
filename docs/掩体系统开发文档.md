| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.0 |

| 适用阶段 | DEMO 基础掩体系统与后续扩展基础 |

# 1. 文档目的

本文件定义项目掩体系统的正式开发架构、数据合同、运行规则、编辑器工作流、迁移方案、开发顺序和验收标准。

本系统不把掩体实现为 Wall、LowCover 上的单个布尔属性，而是建立以下完整链路：

```text
掩体类型配置
    ↓
地图素材的本地方向贡献 / 手动 EdgePlacement
    ↓
TacticalMapBaker
    ↓
TacticalMapDefinition.edges
    ↓
运行时 EdgeIndex / LineQuery / CoverQuery
    ↓
CoverResolver / CombatResolver
    ↓
玩家、AI、UI 和 Debug 复用同一结果
```

系统首版必须满足：

- LowCover 和 Wall 能表达不同等级和不同减伤效果。
- 掩体保护具有明确方向，不是整格无方向状态。
- 素材旋转后，掩体方向同步旋转。
- 玩家和敌人使用完全相同的掩体查询与伤害规则。
- 数值通过 Resource 配置，可以使用 ResourceTables 批量编辑。
- 地图作者正常情况下只需要放置和旋转 Structure 素材。
- Bake 结果确定、可重复，不污染作者数据。
- 编辑器和运行时均能观察掩体来源、方向、等级和结算结果。

# 2. 范围与非目标

## 2.1 本阶段范围

本阶段实现：

- `NONE / HALF / FULL` 三档掩体等级。
- 每种掩体独立的确定性伤害减免系数。
- 同一条边两侧不同的掩体配置。
- Structure 素材根据本地边贡献自动派生运行时 Edge。
- 显式 `TacticalEdgePlacement` 与 Structure 派生 Edge 共存。
- 旧 `cover_mask` 的兼容读取和迁移。
- 运行时 Edge 索引。
- 同楼层直射攻击的方向性掩体查询。
- LOS、弹道阻挡、掩体减伤的职责分离。
- 战斗伤害结算接入。
- AI、玩家攻击和 UI 预览复用查询结果。
- 基础编辑器预览和运行时调试信息。

## 2.2 本阶段非目标

以下内容保留扩展位置，但不要求在首版完成：

- 基于角色姿态、身体部位或连续空间的射线模拟。
- 探头、贴墙、侧身射击动画。
- 随机命中率和随机散布。
- 复杂穿甲、跳弹和多层材质穿透。
- 爆炸冲击波绕墙传播。
- 可破坏掩体的完整耐久与碎裂表现。
- 门窗开关状态与存档恢复。
- 跨楼层连续高度遮挡计算。
- AI 的复杂掩体评分、包抄和预判。

这些功能不得阻塞基础掩体链路交付。

# 3. 术语和规则边界

| 术语 | 含义 |
| --- | --- |
| Cover Level | 掩体分类：NONE、HALF、FULL，主要用于玩法识别、UI 和 AI 分类 |
| Damage Reduction Ratio | 实际伤害减免比例，范围 0.0～1.0 |
| Edge | 两个同楼层水平相邻逻辑格之间唯一的一条共享边 |
| Side A / Side B | 规范化 Edge 两个端点对应的受保护侧 |
| Local Edge Contribution | Structure 素材在自身本地方向上对 Edge 规则的贡献 |
| Explicit Edge | 地图作者通过 Edge 工具直接创建并保存的 `TacticalEdgePlacement` |
| Derived Edge | Baker 根据 Structure 或旧 cover_mask 临时推导的 Edge |
| Line of Fire | 一次攻击从攻击者格到目标格经过的地格和边序列 |
| Cover Query | 根据攻击方向和目标侧查询实际生效掩体的权威计算 |

必须保持以下概念独立：

| 属性 | 回答的问题 |
| --- | --- |
| `cover_profile_a / cover_profile_b` | 目标站在这一侧时受到多少掩体保护 |
| `blocks_movement` | 单位能否穿过这条边 |
| `sight_block` | 视线能否穿过这条边 |
| `projectile_block` | 普通弹道能否穿过这条边 |
| `height` | 边缘遮挡物的物理高度 |
| `destructible` | 边缘是否允许被运行时状态改变 |

`FULL` 不等于必然无法攻击；攻击是否成立先由 LOS 和弹道规则决定。一个允许射击但减伤很高的防弹掩体也可以被分类为 FULL。

# 4. 当前项目基础与缺口

## 4.1 已有基础

当前项目已经具备：

- `TacticalEdgeRules.CoverLevel`：`NONE / HALF / FULL`。
- `TacticalEdgeRules.cover_a / cover_b`：同一条边两侧不同等级。
- `TacticalEdgeKey`：同楼层相邻格的规范化键。
- `TacticalEdgePlacement`：作者数据中的显式边缘放置。
- `MapEdgeData`：Bake 后的运行时边缘数据。
- `TacticalMapDefinition.edges`：地图运行时合同中的 Edge 数组。
- `MapEdgeData.from_placement()`：规范化端点时交换 A/B，保持物理侧语义。
- `TacticalMapBaker._rotated_cover_mask()`：已有四方向旋转算法可供复用。
- ResourceTables 插件：可批量编辑 `.tres` 配置。

## 4.2 当前缺口

| 模块 | 当前状态 | 需要补齐 |
| --- | --- | --- |
| Cell Tile Definition | 只有整格 `rule_contribution` | 增加可选本地 Edge Contribution |
| Cover 数据 | 只有等级，没有独立减伤系数 | 增加 `TacticalCoverProfile` |
| Baker | 只收集显式 Edge；新 Placeable 路径把 `cover_mask` 置为 0 | 合并显式、Structure 派生和旧兼容 Edge |
| GridModel | 只读取 cells/transitions | 加载并索引 edges，移动邻接读取 `blocks_movement` |
| LOS | 只读取整格 `opaque_cells` | 统一遍历经过的 Cell 和 Edge |
| 弹道 | 尚未消费 `projectile_block` | 增加确定性弹道阻挡结果 |
| Cover | 尚无权威查询服务 | 增加 `CoverQuery` 和结果对象 |
| CombatResolver | 直接使用武器基础伤害 | 接入 CoverResolver 计算后的有效伤害 |
| UI/AI | 各自只判断基础 LOS/距离 | 复用统一攻击/掩体查询 |
| 编辑器 | 缺少 Edge 和保护方向可视化 | 增加预览、调试模式和诊断定位 |

# 5. 总体架构

```text
┌──────────────────────────────────────────────────────────┐
│ 内容定义层                                               │
│ TacticalCoverProfile / TacticalEdgeRules                 │
│ TacticalCellTileDefinition.edge_contributions            │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│ 地图作者层                                               │
│ StructureGrid + Rotation                                 │
│ TacticalMapAuthoringData.edge_placements                 │
└──────────────────────────┬───────────────────────────────┘
                           │ Validate / Bake
┌──────────────────────────▼───────────────────────────────┐
│ 编译层                                                   │
│ Explicit Edge + Structure Derived + Legacy cover_mask    │
│ Canonicalize / Merge / Diagnose / Sort                   │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│ 运行时地图合同                                           │
│ TacticalMapDefinition V3                                 │
│ MapCellData + MapEdgeData                                │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│ 运行时规则层                                             │
│ TacticalEdgeIndex → TacticalLineQuery → CoverQuery       │
│                         ↓                                │
│                    CoverResolver                         │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│ 消费层                                                   │
│ CombatResolver / Player / AI / Attack Preview / Debug    │
└──────────────────────────────────────────────────────────┘
```

权威数据边界：

- 作者场景负责表达意图，不作为运行时规则来源。
- `TacticalMapBaker` 是作者数据到运行时地图事实的唯一编译入口。
- `TacticalMapDefinition` 是运行时唯一地图合同。
- `CoverQuery` 是玩家、AI、UI 判断方向性掩体的唯一正式接口。
- `CoverResolver` 是掩体伤害减免的唯一正式计算入口。
- ResourceTables 只负责编辑 Resource，不成为运行时依赖。

# 6. 数据结构设计

## 6.1 TacticalCoverProfile

建议文件：

```text
scripts/core/cover/tactical_cover_profile.gd
```

职责：描述一种可复用的掩体类型和它的实际减伤数值。它不保存地图方向、位置、LOS、弹道、移动或运行时状态。

```gdscript
@tool
class_name TacticalCoverProfile
extends Resource

@export var cover_id: StringName = &"cover.none"
@export var display_name: String = "None"
## 数值合同与 TacticalEdgeRules.CoverLevel 一致：NONE=0、HALF=1、FULL=2。
## 使用独立 int 可以避免 Profile 与 EdgeRules 互相类型引用形成脚本加载环。
@export_enum("NONE", "HALF", "FULL") var cover_level: int = 0
@export_range(0.0, 1.0, 0.01) var damage_reduction_ratio: float = 0.0
@export var debug_color: Color = Color(0.65, 0.65, 0.65)
@export var tags: PackedStringArray = PackedStringArray()
```

字段约定：

| 字段 | 约定 |
| --- | --- |
| `cover_id` | 稳定 ID，不使用显示名作为引用 |
| `display_name` | 面向策划和调试 UI |
| `cover_level` | 分类值，不直接决定伤害公式 |
| `damage_reduction_ratio` | 0.0 不减伤，1.0 完全减免 |
| `debug_color` | Edge 预览和运行时调试颜色 |
| `tags` | 未来 AI、技能和材质识别扩展 |

首版默认资源：

```text
resources/combat/cover_profiles/cover_none.tres
resources/combat/cover_profiles/cover_half.tres
resources/combat/cover_profiles/cover_full.tres
```

首版建议默认值：

| Profile | Level | 减伤系数 | 说明 |
| --- | --- | --- | --- |
| `cover.none` | NONE | 0.00 | 无掩体 |
| `cover.half` | HALF | 0.50 | 基础低掩体验证内容 |
| `cover.full` | FULL | 0.75 | 可攻击情况下的强减伤；完整墙通常会先阻挡射击 |

数值仅为原型默认值，最终由玩法测试调整。

验证规则：

- `cover_id` 必须非空并在 Profile 库中唯一。
- 减伤系数必须在 0.0～1.0。
- `NONE` 且减伤不为 0 时给出 Warning。
- `HALF/FULL` 且减伤为 0 时给出 Warning。
- 同等级允许不同系数，例如木制半掩体 0.35、金属半掩体 0.55。

## 6.2 CoverCombatSettings

建议文件：

```text
scripts/core/cover/cover_combat_settings.gd
resources/combat/cover_combat_settings.tres
```

职责：保存全局结算策略和旧数据回退映射，不保存具体地图内容。

建议字段：

```gdscript
@export var legacy_none_profile: TacticalCoverProfile
@export var legacy_half_profile: TacticalCoverProfile
@export var legacy_full_profile: TacticalCoverProfile
@export_range(0, 999, 1) var minimum_damage_after_cover: int = 0
@export var allow_zero_damage: bool = true
```

首版固定使用 `roundi()`，暂不暴露复杂舍入策略。`damage_reduction_ratio = 1.0` 时，如 `allow_zero_damage` 为 true，结果允许为 0。

## 6.3 TacticalEdgeRules 扩展

保留现有物理字段，增加 Profile 引用：

```gdscript
@export var cover_profile_a: TacticalCoverProfile
@export var cover_profile_b: TacticalCoverProfile
```

旧字段在迁移期保留：

```gdscript
@export var cover_a: CoverLevel
@export var cover_b: CoverLevel
```

解析优先级：

```text
cover_profile_a/b 非空
    > 根据旧 cover_a/b 从 CoverCombatSettings 映射默认 Profile
    > cover.none
```

不得同时让旧等级和新 Profile 分别进入两套结算。所有兼容数据都必须先解析成 `TacticalCoverProfile`，再交给 `CoverQuery`。

## 6.4 TacticalLocalEdgeContribution

建议文件：

```text
scripts/core/map/tactical_local_edge_contribution.gd
```

职责：描述一个 Cell/Structure 素材在某个本地方向上自动产生的 Edge 规则。

```gdscript
@tool
class_name TacticalLocalEdgeContribution
extends Resource

enum LocalDirection {
    NORTH,
    EAST,
    SOUTH,
    WEST,
}

@export var local_direction: LocalDirection = LocalDirection.NORTH
@export var edge_rules: TacticalEdgeRules
@export var enabled: bool = true
```

方向与两侧语义：

1. Baker 先构造未规范化端点：

```text
source_cell → neighbor_cell(source_cell + rotated_direction)
```

2. 在 `TacticalLocalEdgeContribution` 语境下：

```text
edge_rules.cover_profile_a = source_cell 一侧
edge_rules.cover_profile_b = neighbor_cell 一侧
```

3. 转换为规范化 `TacticalEdgeKey` 时，如果端点顺序反转，必须同时交换 A/B Profile。

这一约定可以表达：

- 单侧掩体。
- 双侧掩体。
- 两侧不同等级或系数。
- Structure 占据格与相邻可站立格的不同保护。

## 6.5 TacticalCellTileDefinition 扩展

增加：

```gdscript
@export var edge_contributions: Array[TacticalLocalEdgeContribution] = []
```

职责保持分离：

```text
rule_contribution  → 整格通行、移动、LOS、弹道、高度
edge_contributions → 地格边缘方向、掩体和边缘阻挡
```

一个素材可以没有 Edge Contribution，也可以对四个方向分别提供不同规则。

## 6.6 TacticalEdgePlacement

`TacticalEdgePlacement` 只保存地图作者显式创建的 Edge。

Structure 派生 Edge 不写入：

```text
TacticalMapAuthoringData.edge_placements
```

显式 Edge 用于：

- 门。
- 窗。
- 地格边缘沙袋。
- 栏杆。
- 单侧掩体。
- 与任何整格 Structure 无关的边缘规则。

## 6.7 MapEdgeData 扩展

建议增加：

```gdscript
@export var cover_profile_a: TacticalCoverProfile
@export var cover_profile_b: TacticalCoverProfile
@export var source_type: StringName = &"explicit"
@export var source_layer: StringName = &""
@export var source_cell: Vector3i = Vector3i.ZERO
@export var source_placeable_id: StringName = &""
@export var source_mesh_item_id: int = -1
```

`source_*` 只用于诊断和编辑器定位，不参与伤害计算，不保存 Node 引用。

Profile 必须保留为外部 Resource 引用，不在每张地图中复制一份。这样修改 Profile 后，所有引用该 Profile 的地图共享相同数值定义。

旧 `cover_a / cover_b` 暂时保留，供旧地图和诊断读取。

## 6.8 TacticalMapDefinition V3

接入 Profile 和派生来源后，将：

```gdscript
TacticalMapDefinition.CURRENT_SCHEMA_VERSION
```

升级为 3。

兼容策略：

- Schema 1：旧 GridMap/Catalog。
- Schema 2：存在 Edge，但只有等级。
- Schema 3：Edge 支持 Profile、来源和正式运行时查询。

运行时不得修改 `TacticalMapDefinition` 或其中的共享 Profile Resource。

# 7. Wall 和 LowCover 内容配置

## 7.1 LowCover

现有 `low_cover.tres` 保留：

```text
walkable = false
occluder_height = 0.7
terrain_tags = ["low_cover"]
```

增加与实际模型方向一致的 `edge_contributions`。

示例：如果模型沿本地 North 边放置，并且只保护相邻格一侧：

```text
local_direction = NORTH
source_side = cover.none
neighbor_side = cover.half
sight_block = 0.0
projectile_block = 0.0
height = 0.7
```

如果模型是可从两侧利用的低墙，则两侧都引用 `cover.half`。

不能只按素材名称假设方向。实际配置必须与 MeshLibrary 中模型的本地朝向一致，并通过 0°/90°/180°/270°预览验收。

## 7.2 Wall

现有 `wall.tres` 保留：

```text
walkable = false
sight_block = 1.0
projectile_block = 1.0
occluder_height = 1.6
terrain_tags = ["wall"]
```

根据墙体模型实际占位决定是否增加一个或多个 FULL Edge Contribution。

普通直射攻击穿过完整 Wall 时，预期流程是：

```text
LOS 或 projectile_block 判定失败
    → 攻击被拒绝
    → 不进入 CoverResolver
```

FULL Profile 仍可用于编辑器显示、AI 判断、未来穿透或爆炸规则。

## 7.3 后续边缘素材

以下内容应优先制作成 `TacticalEdgeDefinition`，不应长期依赖整格 Structure 推导：

- 贴地格边缘的沙袋。
- 门与窗。
- 栏杆。
- 单向防弹板。
- 可破坏边界。

Structure 派生 Edge 是常用创作入口和现有内容兼容方式，不替代正式 Edge 作者能力。

# 8. Baker 设计

## 8.1 输入来源

Baker 收集三类 Edge：

1. 显式 `TacticalEdgePlacement`。
2. Structure `edge_contributions` 派生 Edge。
3. 旧 `cover_mask` 兼容 Edge。

## 8.2 纯函数约束

Bake 不得：

- 修改 GridMap 单元格。
- 向 `authoring_data.edge_placements` 写入派生 Edge。
- 自动保存作者场景。
- 因重复 Bake 产生额外作者数据。
- 为了清理旧派生 Edge 修改用户场景。

相同输入连续 Bake 两次，必须产生语义相同、顺序稳定的输出。

## 8.3 Structure 派生算法

对 StructureGrid 每个已使用格：

1. 通过 PlaceableLibrary 查找 `TacticalCellTileDefinition`。
2. 读取 `edge_contributions`。
3. 读取 GridMap 单元格方向 Basis。
4. 将每个本地方向旋转为世界 N/E/S/W。
5. 构造未规范化 `(source_cell, neighbor_cell)`。
6. 复制 EdgeRules，保留 Profile 引用。
7. 规范化 `TacticalEdgeKey`，必要时交换 A/B。
8. 写入本次 Bake 的临时 Edge 集合。
9. 记录来源诊断字段。

方向向量约定：

```text
North = ( 0, 0, -1)
East  = ( 1, 0,  0)
South = ( 0, 0,  1)
West  = (-1, 0,  0)
```

必须复用或提取现有 `_rotated_cover_mask()` 的方向转换逻辑，避免建立第二套旋转规则。

## 8.4 旧 cover_mask 转换

旧掩体掩码只有方向，没有等级。兼容转换统一使用 `CoverCombatSettings.legacy_half_profile`。

每个 mask bit：

```text
source_cell 这一侧 = legacy HALF
neighbor_cell 这一侧 = NONE
```

转换发生在内存中，不回写旧地图。

## 8.5 合并优先级

同一个规范 EdgeKey 出现多个来源时：

```text
显式 Edge
    > Structure 派生 Edge
    > 旧 cover_mask
```

处理规则：

- 高优先级来源覆盖低优先级来源，并产生 Info 诊断。
- 同优先级、规则完全相同：去重并产生 Info 诊断。
- 同优先级、规则不同：Error，禁止 Bake。
- 不允许依赖数组或 Dictionary 的自然顺序决定胜负。

## 8.6 稳定排序

最终 Edge 数组按以下顺序排序：

1. `cell_a.y`。
2. `cell_a.z`。
3. `cell_a.x`。
4. `cell_b.y`。
5. `cell_b.z`。
6. `cell_b.x`。

避免重复 Bake 产生无意义 Git 差异。

## 8.7 Baker 诊断

建议新增稳定诊断代码：

| 代码 | 等级 | 含义 |
| --- | --- | --- |
| `TMB-067` | Error | Structure 派生了非法 EdgeKey；`TMB-060` 已用于无效输出路径 |
| `TMB-068` | Error | 同优先级 Edge 规则冲突；`TMB-061` 已用于资源保存失败 |
| `TMB-062` | Info | 高优先级 Edge 覆盖兼容来源 |
| `TMB-063` | Error | Edge 引用缺失或非法 CoverProfile |
| `TMB-064` | Warning | 掩体保护侧没有有效地图 Cell |
| `TMB-065` | Warning | NONE Profile 配置了非零减伤 |
| `TMB-066` | Info | 相同 Edge 规则被安全去重 |

诊断必须包含 EdgeKey、来源坐标和 Placeable ID，编辑器点击后能够定位。

# 9. 运行时 Edge 索引

## 9.1 TacticalEdgeIndex

建议文件：

```text
scripts/core/map/tactical_edge_index.gd
```

职责：把 `TacticalMapDefinition.edges` 构建成规范键 Dictionary，避免每次攻击线性扫描。

建议接口：

```gdscript
class_name TacticalEdgeIndex
extends RefCounted

func configure(edges: Array[MapEdgeData]) -> bool
func get_edge(cell_a: Vector3i, cell_b: Vector3i) -> MapEdgeData
func has_edge(cell_a: Vector3i, cell_b: Vector3i) -> bool
func is_movement_blocked(cell_a: Vector3i, cell_b: Vector3i) -> bool
func clear() -> void
```

索引键必须来自 `TacticalEdgeKey.key_string()` 或等价稳定值，不得使用两个方向分别保存同一条边。

## 9.2 GridModel 接入

`GridModel.configure_from_definition()` 增加 Edge 加载，并使水平邻接读取 `blocks_movement`。

规则：

- 普通水平相邻格存在，但对应 Edge `blocks_movement = true` 时，不返回为可移动邻居。
- 显式 TraversalLink 不被普通水平 Edge 意外阻挡；是否允许通过由 TraversalLink 自己决定。
- Pathfinding、可移动范围和 AI 寻路必须复用同一个邻接结果。

## 9.3 运行时状态

首版 Edge 为静态数据。

未来门和可破坏掩体不得直接修改共享 `MapEdgeData` Resource，而应通过运行时覆盖层表达：

```text
TacticalEdgeRuntimeStateIndex
    edge_key
    current_state
    movement/sight/projectile/cover overrides
```

当前阶段只保留接口位置，不实现完整状态系统。

# 10. Line of Fire 与 CoverQuery

## 10.1 统一格线追踪

建议新增：

```text
scripts/core/cover/tactical_line_query.gd
scripts/core/cover/tactical_line_query_result.gd
```

一次追踪返回：

```gdscript
cells_crossed
edges_crossed
target_incoming_edges
los_blocked
projectile_blocked
blocking_cell
blocking_edge
```

LOS、弹道和掩体应共享同一条离散格线结果，避免三套算法对斜线和角点给出不同结论。

## 10.2 首版追踪范围

首版支持同楼层攻击：

- 水平直线。
- 斜向线。
- 任意格距内的 Supercover 格线遍历。

跨楼层攻击在首版可以：

- 继续使用当前距离/LOS 兼容逻辑；
- CoverQuery 返回 `unsupported_height_relation` 和 NONE；
- 不得产生崩溃或不稳定结果。

后续再接入眼睛高度、Edge 高度和连续空间射线。

## 10.3 目标入射边规则

方向性掩体只检查射线进入目标格之前的最后一条目标边，而不是检查目标格周围所有掩体。

流程：

1. 从攻击者格中心追踪到目标格中心。
2. 收集经过的 Cell 和 Edge。
3. LOS 或弹道被途中内容完全阻挡时，返回阻挡结果。
4. 找出射线进入目标格的最后 Edge。
5. 如果目标等于该 Edge 的 `cell_a`，读取 `cover_profile_a`。
6. 如果目标等于 `cell_b`，读取 `cover_profile_b`。

## 10.4 角点规则

射线恰好从目标格角落进入时，可能同时存在两条候选入射边。

首版固定规则：

- 两条候选边都进入 `target_incoming_edges`。
- 分别读取目标侧 Profile。
- 选择 `damage_reduction_ratio` 较高者。
- 系数相同时选择更高 CoverLevel。
- 仍相同时按 EdgeKey 稳定顺序选择。

这样可以保证结果与浮点误差、Dictionary 顺序无关。

## 10.5 CoverQueryResult

建议文件：

```text
scripts/core/cover/cover_query_result.gd
```

建议字段：

```gdscript
attacker_cell: Vector3i
target_cell: Vector3i
has_cover: bool
cover_level: TacticalEdgeRules.CoverLevel
profile: TacticalCoverProfile
damage_reduction_ratio: float
source_edge: MapEdgeData
source_edge_key: String
target_side: StringName
los_blocked: bool
projectile_blocked: bool
block_reason: StringName
candidate_edges: Array[MapEdgeData]
```

结果对象创建后按只读约定使用。

## 10.6 CoverQuery 接口

建议文件：

```text
scripts/core/cover/cover_query.gd
```

建议接口：

```gdscript
static func get_cover(
    attacker_cell: Vector3i,
    target_cell: Vector3i,
    grid: GridModel,
    edge_index: TacticalEdgeIndex,
    settings: CoverCombatSettings
) -> CoverQueryResult
```

边界情况：

| 情况 | 结果 |
| --- | --- |
| 攻击者或目标格不存在 | invalid_cell |
| 攻击者与目标同格 | NONE |
| 中途 LOS 完全阻挡 | `los_blocked = true` |
| 中途弹道完全阻挡 | `projectile_blocked = true` |
| 目标入射边不存在 | NONE |
| Edge 存在但目标侧 Profile 为空 | 通过旧等级回退 |
| 斜线角点 | 按稳定最强候选规则 |
| 跨层首版未支持 | NONE + 明确诊断原因 |

# 11. 伤害结算

## 11.1 CoverResolver

建议文件：

```text
scripts/core/cover/cover_resolver.gd
```

首版公式：

```gdscript
reduced_damage = roundi(base_damage * (1.0 - damage_reduction_ratio))
effective_damage = clampi(reduced_damage, minimum_damage_after_cover, base_damage)
```

规则：

- 基础伤害先限制为非负数。
- 系数限制在 0.0～1.0。
- `allow_zero_damage = true` 时，1.0 系数允许得到 0 伤害。
- LOS 或弹道完全阻挡不是“0 伤害命中”，而是攻击验证失败。
- CoverResolver 不读取场景 Node，不扣 HP，只计算数值。

建议返回：

```gdscript
base_damage
effective_damage
prevented_damage
cover_level
cover_profile_id
source_edge_key
```

## 11.2 攻击流程

正式流程：

```text
攻击者/目标有效性
    ↓
AP 与回合验证
    ↓
距离验证
    ↓
TacticalLineQuery
    ↓
LOS 验证
    ↓
Projectile 验证
    ↓
CoverQuery
    ↓
CoverResolver
    ↓
CombatResolver
    ↓
目标扣除 HP
```

`CombatResolver` 仍负责最终 HP 截断、击杀判断和 ActionResult；CoverResolver 负责从基础伤害得到掩体修正后的输入伤害。

## 11.3 ActionResult 调试元数据

建议给通用 `ActionResult` 增加可选：

```gdscript
var metadata: Dictionary = {}
```

攻击结算写入：

```text
base_damage
effective_damage
prevented_damage
cover_level
cover_profile_id
cover_source_edge
```

复制 ActionResult 时必须复制 metadata。其他行动可以忽略该字段。

## 11.4 玩家和敌人统一

以下位置不得分别实现掩体算法：

- 玩家目标高亮。
- 玩家攻击执行。
- 敌人是否攻击判断。
- 敌人攻击执行。
- UI 伤害预览。

它们都应调用统一攻击查询或 `CoverQuery`。敌人攻击不能绕过掩体结算。

# 13. 校验规则

## 13.1 Profile 校验

- ID 非空且唯一。
- 系数范围有效。
- Resource 引用可加载。
- NONE/非零、HALF或FULL/零系数给出语义 Warning。

## 13.2 Edge 校验

- 两端必须同楼层水平相邻。
- EdgeKey 规范化后唯一。
- 至少一侧对应有效地图 Cell。
- 有效保护侧必须能解析为 Profile。
- 来源 Structure 必须能在 PlaceableLibrary 中找到。
- 同优先级冲突禁止 Bake。
- A/B 在规范化和旋转后保持正确。

## 13.3 地图语义校验

- LowCover/Wall 下方仍需满足现有 Floor 规则。
- 掩体边不能引用超出支持楼层范围的坐标。
- 不要求边界外侧必须存在 Floor，但保护不存在的一侧给 Warning。
- `blocks_movement` 的 Edge 不得使必需撤离路径全部失效；继续使用现有可达性校验发现问题。

# 14. 兼容与迁移

## 14.1 迁移原则

- 不要求手工重画现有地图。
- 不修改现有地图 Structure 布局。
- 不覆盖用户对地图场景的美术编辑。
- 旧地图在迁移期仍能加载和 Bake。
- 迁移前后除掩体新效果外，通行、LOS、对象和出生数据保持一致。

## 14.2 迁移步骤

1. 新建默认 NONE/HALF/FULL Profile。
2. 扩展 TacticalEdgeRules 和 MapEdgeData。
3. 增加旧 Level 到默认 Profile 的回退。
4. 增加 TacticalLocalEdgeContribution。
5. 为 LowCover 配置符合模型朝向的 HALF Contribution。
6. 为 Wall 保留整格阻挡，并按模型需要配置 FULL Contribution。
7. Baker 同时读取显式、Structure 派生和旧 cover_mask。
8. 将地图 Schema 升级到 3 并重新 Bake。
9. 对旧、新 Bake 结果执行格子、路径、LOS 与 Edge 数量的语义比较。
10. 所有地图迁移稳定后，把 `cover_mask` 标记为 Deprecated；暂不立即删除字段。

## 14.3 回退策略

如果新 Profile 引用丢失：

- 有旧 CoverLevel 时，使用 `CoverCombatSettings` 默认映射并给 Warning。
- 没有任何可用数据时，回退 NONE 并给 Error；正式 Bake 应失败。

不得静默把非法 FULL 掩体当作 NONE 进入正式构建。

# 18. 测试计划

| FULL | 0.75 | 1 |
| 完全免疫 | 1.00 | 0 |

同时测试：

- 基础伤害 0。
- 目标剩余 HP 小于有效伤害。
- 舍入结果。
- 旧 ActionResult copy 不丢失 metadata。

## 18.5 集成测试

- 玩家攻击目标获得减伤。
- 敌人攻击玩家获得相同减伤。
- UI 预览与实际扣血一致。
- AI 认为可攻击时，执行阶段不会因另一套 LOS/掩体算法产生矛盾。
- GridModel 的 Edge 阻挡影响寻路和移动范围。

## 18.6 地图测试约束

不得为具体可编辑地图场景编写依赖固定布局的测试脚本，也不得使用场景节点数量或某张地图坐标快照作为掩体系统测试依据。

地图、Baker 和 Cover 测试使用运行时创建的合成：

- `TacticalMapDefinition`。
- `MapCellData`。
- `MapEdgeData`。
- `TacticalCellTileDefinition`。
- 小型临时 GridMap/Author 测试夹具。

这样地图内容后续可以自由编辑，不会因为正常地图调整破坏系统测试。

# 19. 性能与确定性要求

- Edge 在地图初始化时建立索引，不在每次攻击时遍历 `definition.edges`。
- CoverQuery 复杂度主要与攻击线长度有关，不与全图 Edge 数量有关。
- Profile 作为共享只读 Resource 使用。
- 所有候选 Edge 使用固定排序和固定比较规则。
- 不使用随机命中或随机掩体减伤。
- Debug 可视化关闭时，不应持续重建全图 Mesh 或 Gizmo。
- 编辑器只在相关 Structure、Edge、楼层或调试筛选变化时刷新预览。

# 20. 风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| Profile 与 EdgeRules 职责重复 | Profile 只负责类型与减伤；EdgeRules 负责空间物理规则 |
| 自动 Edge 与手动 Edge 冲突 | 固定优先级、稳定诊断、Bake 禁止同级歧义 |
| 重复 Bake 污染场景 | 派生 Edge 仅存在于 Bake 临时集合 |
| 素材模型方向与规则不一致 | 四方向编辑器预览和旋转测试作为内容验收 |
| 玩家、AI、UI 结果不同 | 统一 TacticalLineQuery/CoverQuery |
| 斜线角点不稳定 | 固定候选和排序规则 |
| Wall 同时 FULL 与完全阻挡语义混乱 | 先判断 LOS/弹道，再进入减伤；文案分别显示 |
| Profile 删除导致旧地图失效 | 稳定 ID、引用校验和旧等级回退 |
| 地图频繁编辑导致测试脆弱 | 测试使用合成地图数据，不绑定正式地图场景 |

# 21. 系统完成定义

掩体系统只有同时满足以下条件才视为完成：

1. LowCover 和 Wall 都通过正式数据定义接入，不使用名称判断或专用代码分支。
2. 掩体方向与 Structure 旋转一致。
3. MapDefinition 中存在可查询的正式 Edge 数据。
4. 重复 Bake 幂等且不修改作者场景。
5. 运行时使用 EdgeIndex，不线性扫描全图 Edge。
6. 玩家和敌人使用同一 CoverQuery 和 CoverResolver。
7. UI 伤害预览与实际伤害一致。
8. LOS、弹道阻挡和掩体减伤保持独立。
9. 编辑器能显示 Edge、保护侧、等级、系数和冲突。
10. 修改 Profile 可以改变玩法数值而无需修改代码。
11. 可以只通过新建一个 Profile 和配置已有贡献，增加至少一种新掩体内容。
12. 数据、Baker、查询、结算和集成测试全部通过。

# 23. 最终原则

本系统的正式边界为：

> `TacticalCoverProfile` 定义“这种掩体减多少伤害”；`TacticalEdgeRules` 定义“这条物理边如何影响两侧、移动、视线和弹道”；Baker 把地图作者意图编译成 `MapEdgeData`；`CoverQuery` 决定本次攻击实际使用哪一侧掩体；`CoverResolver` 负责确定性减伤；玩家、AI、UI 和 Debug 复用同一结果。

不得把掩体重新退化为素材名称判断、整格布尔值或只存在于视觉模型中的隐式规则。

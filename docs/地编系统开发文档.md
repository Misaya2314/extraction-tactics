# 1. 文档目的

本文档定义战术地图编辑系统的完整技术架构、数据契约、编辑流程、扩展方式、开发顺序和验收标准，作为后续任务拆分、接口约定和最终验收的统一依据。

本系统需要解决以下问题：

- 地图设计者可以从统一素材栏选择地面、墙体、掩体、装饰和玩法对象，并直接在 3D 场景中放置。
- 地图设计者不需要频繁操作场景树、手工填写 MeshLibrary 数字 ID 或理解底层存储位置。
- 新增一种地格或地图元素时，优先通过资源配置完成，不修改核心代码。
- 地格具有可配置的玩法属性，例如移动预算消耗、通行、视线阻挡、弹道阻挡和遮挡高度。
- 全局默认属性修改后，可以自动影响所有未单独覆盖的实例。
- 允许对地图中的单个或一组地格进行局部属性覆盖。
- 支持多楼层、显式跨层连接、边缘掩体、物资点、出生点、撤离点和巡逻路线。
- 编辑器数据通过统一校验和烘焙进入运行时，玩法系统不直接依赖编辑器 UI。
- 当前地图和现有 `GridModel`、寻路、LOS、对象生成流程能够渐进迁移，不整体推翻。

本文档是新地编系统的技术设计。现有《地图制作与三维地格系统》继续用于描述旧/当前操作流程；开发新系统时以本文档为准。《三维地格坐标中心契约》继续作为坐标换算的权威约定。

# 2. 形式选择结论

## 2.1 最终形式

系统采用：

> **项目内 Godot 编辑器插件 + 独立核心数据/编译层 + 现有运行时地图层。**

不是以下任一种单独方案：

- 不是只依赖 Godot 原生 GridMap 面板。
- 不是把全部逻辑写进一个大型 `@tool` 节点。
- 不是完全重写 GridMap 的自制体素引擎。
- 不是当前阶段制作玩家可进入的运行时 MC 创造模式。

## 2.2 为什么外层应做成 EditorPlugin

编辑器插件负责用户工作流，适合实现：

- 统一地块/元素素材栏。
- 3D 视口画笔、擦除、吸管、区域填充和边缘放置。
- 当前楼层、目标层和可视化模式切换。
- 自定义属性面板。
- 预览模型、方向箭头和错误 Gizmo。
- 编辑器原生 Undo/Redo。
- 保存提示、校验、烘焙和快捷运行。

Godot 4.7 的 `EditorPlugin` 可以接收 3D 视口输入、添加 Dock、Inspector 扩展和 3D Gizmo；`EditorUndoRedoManager` 可以把插件操作接入场景的撤销历史。参考：

- [EditorPlugin](https://docs.godotengine.org/en/4.7/classes/class_editorplugin.html)
- [EditorUndoRedoManager](https://docs.godotengine.org/en/4.7/classes/class_editorundoredomanager.html)
- [EditorNode3DGizmoPlugin](https://docs.godotengine.org/en/4.7/classes/class_editornode3dgizmoplugin.html)

## 2.3 为什么核心数据不能全部放进插件

插件只负责编辑体验。以下内容必须位于插件之外：

- 稳定的地格/地图元素定义。
- 地图作者数据结构。
- 属性合并规则。
- 校验器和 Baker 核心。
- 烘焙后的 `TacticalMapDefinition`。
- 运行时 `GridModel`、LOS、掩体、寻路等接口。

这样可以保证：

- 禁用插件不会破坏运行时地图。
- Baker 可以在无界面模式下运行。
- 将来替换编辑器 UI 时不需要迁移玩法数据。
- 将来如果需要运行时地图编辑器，可以复用定义、放置命令、校验和烘焙核心，只重新实现输入与界面。

# 3. 范围与非目标

## 3.1 本系统范围

- 方形三维战术地格的可视化编辑。
- 多楼层地图。
- 地面、结构、装饰、边缘元素和玩法对象的统一放置入口。
- 地格默认规则和单格覆盖。
- 物资点、出生点、撤离点、巡逻路线、跨层连接的便捷配置。
- 地图校验、烘焙、调试可视化和运行时数据生成。
- 现有原型地图兼容迁移。

## 3.2 当前明确不做

- 玩家在正式游戏内使用的地图编辑器。
- 任意体素挖掘、堆叠和运行时逐块破坏世界。
- 地形雕刻、布尔建模或替代 Blender 的模型制作功能。
- 完整程序化地图生成。
- 多人实时协同编辑同一地图。
- 第一阶段即实现复杂自动铺路、自动墙角和 Wave Function Collapse。
- 第一阶段即实现超大世界流式分块。

上述能力可以在核心模型稳定后按实际需求增量开发，不为未知需求提前构建复杂框架。

# 4. 当前项目基础

## 4.1 已有链路

当前项目已经具备：

```text
TacticalMapAuthor 作者场景
├── FloorGrid
├── StructureGrid
├── DecorationGrid
├── Objects
├── Spawns
├── PatrolRoutes
└── TraversalLinks
        ↓
MapTileCatalog + MapTileRule
        ↓
TacticalMapBaker
        ↓
TacticalMapDefinition
        ↓
GridModel / PrototypeController / LOS / AI / 对象生成
```

已有能力包括：

- `Vector3i(x, level, z)` 三维逻辑地格。
- 同层四方向移动，跨层只通过显式 `TraversalLink3D`。
- `GridMap.map_to_local()` 一致的地格中心契约。
- Floor、Structure、Decoration 三层表现结构。
- 地格通行、移动代价、LOS 阻挡、遮挡高度和旧式 `cover_mask`。
- 出生、巡逻、对象、Loot、撤离和跨层连接 Marker。
- 校验后生成只读运行时地图定义。
- 加权寻路和稀疏地格。

## 4.2 当前主要不足

| 问题 | 影响 |
| --- | --- |
| 玩法规则通过 MeshLibrary 数字 `item_id` 绑定 | MeshLibrary 重排或重建后存在语义漂移风险 |
| Floor/Structure/Decoration 需要分别选中 | 地图设计者需要理解底层场景结构 |
| 没有统一素材栏 | 地格、对象、出生点和跨层链接工作流割裂 |
| 没有单格属性覆盖 | 无法方便制作局部特殊地形 |
| 没有属性热力图和边缘可视化 | 行动力、阻挡和掩体规则难以观察 |
| `cover_mask` 属于整格数据 | 无法完整表达双侧、单侧、门或可破坏边缘 |
| 新增地格需要手动维护 MeshLibrary 和 Catalog | 内容扩展容易出错，不符合低门槛目标 |
| Inspector 按钮是主要操作入口 | 可以校验和烘焙，但不构成完整地编体验 |
| 部分编辑操作没有统一 Undo/Redo | 连续生产地图时存在误操作和数据丢失风险 |

## 4.3 保留与替换策略

保留：

- Godot `GridMap` 和 `MeshLibrary`。
- `TacticalMapAuthor` 作者场景入口。
- `TacticalMapBaker` 的纯逻辑编译方向。
- `TacticalMapDefinition` 运行时合同。
- `GridModel`、坐标契约、Marker 和现有玩法系统。

新增：

- Tactical Map Builder 编辑器插件。
- 稳定 ID 的可放置元素定义库。
- 单格覆盖和边缘元素作者数据。
- 放置适配器、编辑会话和事务式 Undo/Redo。
- 新增元素向导和调试可视化。

逐步淘汰：

- 由 `MapTileRule.item_id` 直接充当玩法身份的做法。
- 将掩体长期保存在 `MapCellData.cover_mask` 中的做法。
- 通过节点名称、模型名称或硬编码路径推断玩法规则的做法。

# 5. 设计原则

## 5.1 使用体验与底层存储分离

使用者只看到统一素材栏和统一画笔，不需要知道某个元素最终存入：

- FloorGrid。
- StructureGrid。
- DecorationGrid。
- Edge authoring data。
- Objects/Spawns/TraversalLinks 节点。

插件通过放置适配器自动路由。

## 5.2 内容与系统分离

地格、墙、宝箱等是数据内容；放置、校验、寻路和烘焙是系统。新增同类型内容时优先新增 `.tres` 定义，不新增专用代码分支。

## 5.3 稳定 ID 是玩法身份

例如：

```text
terrain.factory.floor_concrete
terrain.factory.floor_metal
structure.factory.wall_full
cover.factory.crate_half
object.loot.weapon_box
marker.extraction.standard
```

MeshLibrary 数字 item ID 只是视觉适配器内部编号。运行时和存档不得依赖该数字表达内容语义。

## 5.4 默认属性与实例覆盖分离

- 类型定义保存“这一类地格通常是什么”。
- 地图覆盖保存“这一个实例有什么特殊之处”。
- 运行时定义保存合并后的最终结果。

## 5.5 规则与表现分离

模型、材质、缩略图和预览负责表现；通行、AP、LOS、弹道和掩体负责规则。替换 Kenney 模型不应自动改变玩法规则。

## 5.6 单一权威来源

- 坐标换算以现有三维地格中心契约为准。
- 有效地格属性以 Baker 合并结果为准。
- 运行时移动、AI 和 UI 读取同一 `GridModel` 结果。
- 掩体判定由未来 Cover 系统统一计算，编辑器只生产数据和预览。

## 5.7 足够扩展，避免无限抽象

第一版只支持已经明确的地面、结构、边缘、对象和模板四种放置方式。未知的复杂地形或程序生成需求不提前加入核心接口。

# 6. 总体架构

```text
┌────────────────────────────────────────────┐
│  内容定义层                                │
│  TacticalPlaceableLibrary                  │
│  CellTile / Edge / Object / Stamp          │
└──────────────────────┬─────────────────────┘
                       │ 选择内容
┌──────────────────────▼─────────────────────┐
│  编辑器应用层（EditorPlugin）              │
│  Palette / Tools / Selection / Inspector   │
│  Preview / Gizmo / UndoRedo / Diagnostics  │
└──────────────────────┬─────────────────────┘
                       │ 放置事务
┌──────────────────────▼─────────────────────┐
│  作者数据层                                │
│  GridMaps + MapAuthoringData + Markers     │
└──────────────────────┬─────────────────────┘
                       │ Validate / Bake
┌──────────────────────▼─────────────────────┐
│  编译层                                    │
│  Rule Merge / Validator / Migrator / Baker │
└──────────────────────┬─────────────────────┘
                       │ 确定性输出
┌──────────────────────▼─────────────────────┐
│  运行时层                                  │
│  TacticalMapDefinition → GridModel         │
│  LOS / Cover / AI / Spawn / Loot / Save    │
└────────────────────────────────────────────┘
```

依赖方向只能自上而下：

- 运行时层不得依赖 EditorPlugin。
- 定义层不得依赖具体 UI 控件。
- Baker 不得通过节点名称猜测规则。
- UI 不得自行复制寻路、LOS 或掩体算法。

# 7. 内容定义层

## 7.1 TacticalPlaceableDefinition

统一素材栏中所有条目的基础 Resource。

建议字段：

```gdscript
class_name TacticalPlaceableDefinition
extends Resource

@export var schema_version: int
@export var placeable_id: StringName
@export var display_name: String
@export var description: String
@export var category: StringName
@export var tags: PackedStringArray
@export var thumbnail: Texture2D
@export var placement_kind: PlacementKind
@export var enabled_in_palette: bool = true
```

`placeable_id` 必须全项目唯一。修改 ID 属于数据迁移操作，不能当作普通改名。

## 7.2 定义类型

### TacticalCellTileDefinition

用于放入 GridMap 的规则地格：

- 地面。
- 墙体。
- 整格障碍。
- 网格装饰。

建议字段：

- `target_layer`：Floor、Structure、Decoration。
- `mesh_library`：视觉库引用。
- `mesh_item_id`：视觉适配器内部编号。
- `allowed_rotations`：DEMO 默认四方向 Y 轴旋转。
- `footprint`：第一版固定 `1×1×1`，接口保留扩展。
- `rule_contribution`：该元素对有效格规则的贡献。
- `preview_scene`：可选的高质量编辑器预览。

### TacticalEdgeDefinition

用于地格边缘：

- 半掩体。
- 全掩体。
- 门。
- 窗。
- 栏杆。
- 可破坏边界。

建议字段：

- `edge_rules`。
- `visual_scene` 或边缘 Mesh。
- `allowed_directions`。
- `supports_boundary_edge`。
- `default_state`，例如门默认开启/关闭。

### TacticalObjectDefinition

用于实例化或配置 Marker：

- Loot 箱。
- 爆炸桶。
- 普通环境互动对象。
- 撤离点。
- 单位出生点模板。

建议字段：

- `marker_kind`。
- `scene`。
- `default_configuration`。
- `footprint`。
- `requires_floor`。
- `unique_id_prefix`。

地图中的每一个对象实例仍拥有独立 `object_id`。定义 ID 表示对象类型，实例 ID 表示地图中的具体对象。

### TacticalStampDefinition

用于组合模板：

- 一间房。
- 一个楼梯组。
- 一段走廊。
- 一组工厂货架。
- 一个遭遇区域基础布局。

Stamp 保存相对原点的多个放置记录。第一版插件完成后再实现，不阻塞基础画笔。

## 7.3 TacticalPlaceableLibrary

项目级素材库 Resource，保存可用 Definition 引用和内部索引：

```gdscript
class_name TacticalPlaceableLibrary
extends Resource

@export var schema_version: int
@export var definitions: Array[TacticalPlaceableDefinition]
@export var generated_mesh_library: MeshLibrary
@export var item_bindings: Array[MeshItemBinding]
```

职责：

- 校验稳定 ID 唯一。
- 提供分类、标签和搜索索引。
- 映射 `GridMap item_id → placeable_id`。
- 为新增元素向导分配不重复的内部 item ID。
- 删除定义后保留 item ID tombstone，不立即复用旧编号。
- MeshLibrary 重建时保持已有绑定稳定。

每个可放置元素建议独立保存为一个 `.tres`，Library 只保存引用，以减少多人修改不同内容时的 Git 冲突。

## 7.4 新增元素向导

向导流程：

1. 选择元素类型：地格、边缘、对象或模板。
2. 输入稳定 ID、名称、分类、标签和描述。
3. 选择 Mesh、现有 MeshLibrary item 或 PackedScene。
4. 设置目标层、旋转规则和占地。
5. 设置默认玩法规则。
6. 设置或生成碰撞和预览。
7. 自动生成缩略图。
8. 写入独立 Definition `.tres`。
9. 更新 Library 和内部 MeshLibrary 映射。
10. 完成校验后立即出现在素材栏。

第一阶段可以只支持“引用现有 MeshLibrary item”；自动从任意模型生成碰撞和 MeshLibrary 项作为后续增强，不阻塞核心系统。

# 8. 地格规则模型

## 8.1 TacticalCellRules

表示一个地格最终可供运行时使用的规则状态。

首版字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `walkable` | bool | 单位是否允许进入 |
| `move_cost` | int，至少 1 | 进入该格占用的移动预算 |
| `sight_block` | float，0～1 | 视线阻挡程度 |
| `projectile_block` | float，0～1 | 弹道阻挡程度 |
| `occluder_height` | float | 遮挡物相对地格表面的高度 |
| `sound_cost` | float，至少 0 | 声音传播代价，首版可以不接玩法 |
| `terrain_tags` | PackedStringArray | 金属、泥地、室内、危险等标签 |
| `hazard_id` | StringName | 可选地形效果标识 |

当前 `blocks_los: bool` 迁移为：

- `false → sight_block = 0.0`
- `true → sight_block = 1.0`

在完整高度 LOS 实现前，运行时可以继续将 `sight_block >= 1.0` 视为完全阻挡。新增浮点字段是为了给烟雾、玻璃或软遮挡保留已知扩展空间，不要求第一阶段实现概率视线。

当前项目中一次正式 Move Action 固定消耗 `1 AP`，单位同时拥有独立的 `move_range`。因此本节的 `move_cost` 只参与路径成本和一次移动允许到达的范围，不直接改变 Move Action 的 AP 消耗。以后若策划决定让地形同时影响 AP，应由 Action/Movement 规则统一换算，不能在地图编辑器中暗自形成第二套 AP 规则。

## 8.2 固定合并规则

Baker 以地格默认值为起点，按 Floor、Structure、实例覆盖顺序合并。

类型贡献采用固定、可预测规则：

| 属性 | Floor/Structure 合并方式 |
| --- | --- |
| `walkable` | 逻辑 AND，任一元素阻挡即不可走 |
| `move_cost` | 取最大值，保持当前 Baker 语义 |
| `sight_block` | 取最大值 |
| `projectile_block` | 取最大值 |
| `occluder_height` | 取最大值 |
| `sound_cost` | 取最大值，后续需求明确后可版本化调整 |
| `terrain_tags` | 并集 |
| `hazard_id` | Floor 提供默认值，实例覆盖可替换 |

不在各 Definition 中加入任意脚本回调决定合并方式，避免同一规则出现多个来源。

## 8.3 TacticalCellOverride

单格覆盖数据：

```gdscript
class_name TacticalCellOverride
extends Resource

@export var coordinate: Vector3i
@export_flags(...) var override_mask: int
@export var values: TacticalCellRules
```

每个字段在编辑器中显示：

- “继承”复选框。
- 默认值。
- 覆盖值。
- 最终有效值。

不能使用 `-1`、空字符串或特殊布尔值代表继承。是否覆盖只由 `override_mask` 决定。

## 8.4 多格批量编辑

选择多个地格后：

- 全部值相同则显示该值。
- 值不同则显示“混合值”。
- 修改一个字段只写入该字段的 override bit。
- “恢复继承”只清除对应 bit，不删除其他覆盖。
- 空的 override 记录自动移除。

# 9. 边缘模型与掩体数据

## 9.1 为什么边缘必须成为一等数据

旧 `cover_mask` 只能表达某格四边是否有掩体，难以表达：

- 两侧不同效果。
- 半掩体和全掩体。
- 门的开启/关闭状态。
- 可破坏边缘。
- 同一边对移动、LOS 和弹道的不同影响。
- 边缘元素的独立视觉和实例配置。

因此新系统以 `TacticalEdgePlacement` 保存物理边缘。

## 9.2 TacticalEdgeKey

一条共享边只保存一次。建议使用两个相邻逻辑坐标作为规范化键：

```gdscript
class_name TacticalEdgeKey
extends Resource

@export var cell_a: Vector3i
@export var cell_b: Vector3i
```

约定：

- `cell_a`、`cell_b` 按固定 y/z/x 顺序排序。
- 两者必须是同层水平相邻坐标。
- 边界边允许其中一个坐标不是有效地格。
- 查询 N/E/S/W 时统一转换为同一规范键，避免相邻格重复放置同一边。

## 9.3 TacticalEdgeRules

首版字段：

| 字段 | 含义 |
| --- | --- |
| `cover_a` / `cover_b` | 从两侧获得的 NONE/HALF/FULL 掩体等级 |
| `blocks_movement` | 是否阻止穿越该边 |
| `sight_block` | 视线阻挡程度 |
| `projectile_block` | 弹道阻挡程度 |
| `height` | 物理遮挡高度 |
| `destructible` | 是否可破坏 |
| `runtime_state_id` | 门或可破坏物的可选运行时状态标识 |

边缘数据负责描述地图事实；实际伤害减免、命中或侧翼判定仍由独立 Cover 系统决定。

## 9.4 编辑方式

- 选择边缘元素后，鼠标靠近地格边界时自动吸附。
- 幽灵预览显示具体边和有效/无效状态。
- 点击放置，右键擦除。
- `R` 切换方向或双侧配置。
- 旋转/移动选区时同步变换 EdgeKey 和两侧规则。
- 调试模式使用颜色和箭头显示半掩体、全掩体及阻挡方向。

1. level/y。
2. z。
3. x。
4. 边缘另一端坐标或对象 ID。

# 11. 编辑器插件架构

## 11.1 插件入口

`TacticalMapEditorPlugin extends EditorPlugin` 负责：

- 注册/注销 Dock、Inspector 和 Gizmo 插件。
- 识别当前选中的 `TacticalMapAuthor`。
- 创建和销毁 `MapEditSession`。
- 接收 3D 视口输入。
- 管理编辑器状态保存。
- 连接 Undo/Redo、保存、校验和 Bake。

插件只有在以下条件同时满足时消费 3D 输入：

- 当前场景存在有效 `TacticalMapAuthor`。
- 地图编辑模式已开启。
- 当前工具需要处理该输入。

其他情况下返回 PASS，不能破坏 Godot 原生选择、相机和普通场景编辑。

## 11.2 MapEditSession

表示当前作者场景的一次编辑会话：

- 当前 Author。
- 当前 Library。
- 当前楼层。
- 当前目标层。
- 当前工具。
- 当前选中的 Definition。
- 当前旋转。
- 当前选区。
- 当前调试可视化模式。
- 未提交画笔 stroke。
- 未保存外部数据状态。

切换场景或 Author 时必须安全结束 stroke，并恢复对应场景的编辑状态。

## 11.3 放置适配器

统一接口示意：

```gdscript
interface TacticalPlacementAdapter
    can_place(context, definition, target) -> PlacementCheck
    capture_before(context, target) -> Variant
    apply(context, definition, target, rotation) -> void
    erase(context, target) -> void
    pick(context, target) -> TacticalPlaceableDefinition
    restore(context, snapshot) -> void
```

首版适配器：

- `CellPlacementAdapter`：写入 Floor/Structure/Decoration GridMap。
- `EdgePlacementAdapter`：写入 `TacticalMapAuthoringData.edge_placements`。
- `ObjectPlacementAdapter`：创建/删除对应 Marker 节点。
- `StampPlacementAdapter`：后续批量调用前三类适配器。

UI 不直接调用 `GridMap.set_cell_item()` 或创建 Marker，避免工具逻辑和存储方式耦合。

## 11.4 PlacementTarget

视口拾取得到统一目标：

```gdscript
class_name PlacementTarget
extends RefCounted

var cell: Vector3i
var edge: TacticalEdgeKey
var world_position: Vector3
var surface_normal: Vector3
var current_level: int
var valid: bool
var reason: String
```

Cell 工具使用 `cell`，Edge 工具使用 `edge`，对象工具使用格心和方向。高层编辑不能把射线固定投影到 Y=0。

## 11.5 视口交互

最小工具集：

| 工具 | 行为 |
| --- | --- |
| Paint | 左键或拖动连续放置 |
| Erase | 删除当前类型/层的内容 |
| Pick | 从目标位置吸取元素和旋转 |
| Select | 单选、框选和多选 |
| Rectangle | 矩形填充 |
| Fill | 连通区域填充，同层执行 |
| Move/Duplicate | 携带几何、覆盖和边缘移动/复制 |
| Edge Paint | 吸附地格边缘放置 |
| Stamp | 放置组合模板，后续阶段实现 |

建议快捷键：

- 左键：放置/确认。
- 右键：擦除当前通道。
- 中键：吸取。
- `R`：顺时针旋转 90°。
- `Shift`：矩形或扩展选区。
- `Ctrl + 滚轮`：切换楼层。
- `Delete`：删除选区。
- `Esc`：取消当前操作。

快捷键应在插件设置中可调整，并避免覆盖 Godot 无法转发的关键编辑器操作。

## 11.6 创造模式素材栏

Dock 至少包括：

- 分类页签。
- 搜索框。
- 标签筛选。
- 缩略图网格。
- 收藏和最近使用。
- 当前 Definition 详情。
- 新增、复制和编辑 Definition 按钮。
- Validate、Bake、Play Map 按钮。

默认分类：

- 地面。
- 墙体/结构。
- 掩体/边缘。
- 装饰。
- 互动对象。
- Loot。
- 出生/撤离。
- 跨层。
- 模板。

素材栏可以使用 `EditorDock`，但该类在 Godot 4.7 中仍标记为 experimental。插件应通过单独的 Dock Host 类封装注册逻辑，避免未来引擎升级时影响编辑核心。

## 11.7 属性面板

选中 Definition：

- 编辑全局默认属性。
- 明确提示影响所有未覆盖实例。
- ID 修改必须进入迁移流程。

选中地图地格：

- 显示坐标、层、Floor/Structure 内容。
- 显示默认值、覆盖值和最终有效值。
- 提供逐字段继承/覆盖开关。
- 支持多选批量修改。

选中边缘/对象：

- 显示定义和实例配置。
- 对门、Loot、出生点等提供对应配置控件。

## 11.8 幽灵预览和错误反馈

鼠标悬停时显示半透明预览：

- 绿色：允许放置。
- 黄色：允许但存在警告。
- 红色：禁止放置，并显示简短原因。

禁止放置的常见原因：

- 超出地图体积。
- 目标层不匹配。
- Structure 下没有 Floor。
- 同一层同格已有内容且当前工具不允许替换。
- 对象缺少有效地面。
- 边缘方向非法。
- Stamp 与已有重要对象冲突。

# 12. Undo/Redo、保存与事务

## 12.1 编辑事务

每次操作由 `PlacementTransaction` 收集：

- 受影响 GridMap cell 的旧值和新值。
- 受影响 CellOverride 的旧值和新值。
- 受影响 EdgePlacement 的旧值和新值。
- 新增/删除 Marker 节点及 owner。
- 选区变换前后的数据。

一个连续 stroke 只提交一个 Undo Action。不能每经过一个地格就创建一条撤销记录。

## 12.2 必须支持撤销的行为

- 放置和擦除。
- 连续拖动画笔。
- 矩形/区域填充。
- 选区移动、复制、旋转和镜像。
- 单格和批量属性覆盖。
- 添加、删除和修改边缘。
- 添加、删除和修改 Marker。
- Stamp 放置。
- 新增 Definition 和 Library 绑定。

## 12.3 保存策略

- 场景几何随 `.tscn` 保存。
- 外部 `TacticalMapAuthoringData` 由插件随项目/场景保存写入。
- 插件维护 dirty 状态，并在关闭时提供明确提示。
- Bake 使用当前内存数据，但不得隐式丢弃未保存的作者修改。
- Baker 失败时不覆盖上一次有效运行时资源。

# 14. Baker 与 Validator

## 14.1 Baker 输入

- `TacticalMapAuthor` 配置。
- Floor/Structure/Decoration GridMap。
- `TacticalPlaceableLibrary`。
- `TacticalMapAuthoringData`。
- 当前 Marker、路线和跨层节点。

Decoration 默认不进入玩法规则，只在作者场景中保留表现；若未来某个装饰需要玩法能力，应改为 Structure、Edge 或 Object Definition。

## 14.2 编译顺序

1. 校验 Author、Library、尺寸、Transform 和数据版本。
2. 读取并排序 Floor cells。
3. 通过 Library 将 item ID 解析为稳定 Definition ID。
4. 创建基础有效地格规则。
5. 合并 Structure 贡献和旋转后的方向数据。
6. 应用 `TacticalCellOverride`。
7. 编译 EdgePlacement。
8. 收集对象、出生、巡逻和跨层连接。
9. 运行结构校验和玩法校验。
10. 生成固定排序的 `TacticalMapDefinition`。
11. 仅在无 Error 时保存。

## 14.3 结构校验

- 地图 ID、资源路径和 schema version 有效。
- 必需 GridMap 存在，Transform 和 cell size 一致。
- Library ID 唯一，所有 item 都能解析。
- Floor、Structure、Override 和 Edge 坐标在声明体积内。
- Structure 默认要求下方同格存在 Floor。
- Override 不引用不存在的有效格。
- EdgeKey 合法且无重复。
- Marker ID 唯一。
- 对象场景、Loot Table、武器和单位配置引用有效。
- TraversalLink 两端存在且不是同格。

## 14.4 玩法校验

- 至少有一个玩家出生点。
- 至少有一个撤离点。
- 出生点位于可走地格且不重复占格。
- 玩家出生点能够抵达至少一个撤离点。
- 巡逻路线点存在，连续点可达。
- Loot/撤离/互动对象位于合法位置。
- 门或阻挡边的初始状态不会让必需路线永久失效，无法确定时给 Warning。
- 高价值 Loot、遭遇区域等策划规则作为后续可选 Validator，不写死进基础 Baker。

## 14.5 错误等级

- Error：禁止 Bake，必须修复。
- Warning：允许 Bake，但在视口和报告中显示。
- Info：统计和建议，不影响流程。

每条问题包含：

- 稳定问题代码。
- 人类可读说明。
- 关联坐标或对象 ID。
- 可选修复建议。

插件点击问题时应定位到对应格、边或 Marker。

# 15. 运行时地图合同

## 15.1 TacticalMapDefinition V2

运行时定义继续是 Baker 的唯一正式输出。建议升级 schema，并逐步增加：

- `cells: Array[MapCellDataV2]`
- `edges: Array[MapEdgeData]`
- `transitions`
- `spawns`
- `patrol_routes`
- `objects`
- `source_content_hash`

`MapCellDataV2` 保存合并后的最终值和稳定内容标识，不保存编辑器 override mask。

## 15.2 运行时边界

- `GridModel` 负责地格存在、占用、移动代价、邻接和路径。
- LOS 系统读取最终视线阻挡和高度数据。
- Cover 系统读取 EdgeData 并提供统一掩体查询。
- AI、玩家行动和 UI 复用 Grid/LOS/Cover 的正式查询接口。
- MapDefinition 不保存单位当前 HP、门当前状态或容器已搜刮状态；这些属于运行时状态和存档数据。

## 15.3 动态对象状态

门、可破坏掩体等状态变化必须通过运行时接口同步影响：

- Grid movement edge。
- LOS/弹道阻挡。
- Cover 查询。
- 可视化和 UI。

不能只切换模型表现。

# 16. 兼容迁移方案

## 16.1 迁移原则

- 不手工重画现有地图。
- 不覆盖用户当前地图美术修改。
- 迁移前后有效地格、移动代价、通行、LOS、对象和跨层语义一致。
- 旧 Catalog 在一个过渡阶段内可读，完成全部地图迁移后再删除。

## 16.2 迁移步骤

1. 为当前 Floor、FloorAlt、Wall、LowCover 创建稳定 Definition。
2. 从现有 `MapTileRule` 复制默认属性。
3. 建立现有 MeshLibrary item ID 到稳定 ID 的 Library binding。
4. 保留现有 GridMap cell 数据，不修改布局。
5. Baker V2 优先读取新 Library，必要时使用旧 Catalog 兼容适配器。
6. 将当前地图 Bake 为 V2，并与旧 Bake 的有效规则进行语义比较。
7. Edge 系统完成前保留 `cover_mask` 兼容字段。
8. Edge 系统完成后，把每个旋转后的 `cover_mask` 转换为 EdgePlacement。
9. 所有地图迁移并验收后，标记旧 `MapTileCatalog/MapTileRule` 废弃。

## 16.3 ID 改名迁移

Definition 的稳定 ID 不允许直接编辑并静默保存。必须通过迁移工具：

- 输入旧 ID 和新 ID。
- 检查新 ID 冲突。
- 更新 Library、Stamp 和地图作者数据引用。
- 生成 alias 记录供旧运行时资源或存档过渡读取。
- 输出迁移报告。

# 18. 开发阶段

## 阶段 A：数据基础与兼容层

目标：建立不会被 UI 绑死的正式数据合同。

内容：

- Placeable Definition 和 Library。
- CellRules、CellOverride、EdgeKey/Rules/Placement。
- AuthoringData。
- 固定合并规则。
- Library item binding。
- 旧 Catalog 迁移和兼容读取。
- TacticalMapDefinition schema 升级准备。

验收门槛：

- 当前地图无需重画。
- 新旧 Baker 的有效地格语义一致。
- 稳定 ID 冲突和缺失能被发现。

## 阶段 B：编辑器插件 MVP

目标：完成真正可用的创造模式基础工作流。

内容：

- 插件入口和 Dock。
- 素材栏、分类、搜索。
- Author 识别、楼层和目标层。
- Paint、Erase、Pick、Rotate。
- 幽灵预览。
- Cell/Object 放置适配器。
- Stroke 级 Undo/Redo。
- Save、Validate、Bake、Play Map。

验收门槛：

- 不操作场景树即可完成基础地面、墙、装饰和对象摆放。
- 一个 stroke 可以整体撤销和重做。
- 保存重开后结果一致。

## 阶段 C：属性编辑与诊断

目标：让地格玩法属性可编辑、可观察、可批量处理。

内容：

- 单格和多格选择。
- 继承/覆盖属性面板。
- 批量修改和恢复继承。
- Walkability、Move Cost、Sight、Projectile、Height 可视化。
- Validation 列表和视口定位。

验收门槛：

- 修改默认值能影响全部未覆盖实例。
- 修改单格覆盖只影响目标实例。
- 调试视图与 Baker 最终值一致。

## 阶段 D：边缘与掩体作者能力

目标：先完成掩体系统所需的正式地图数据入口。

内容：

- EdgePlacementAdapter。
- 边缘吸附、方向预览、擦除、移动和旋转。
- 半/全掩体数据。
- 门和移动/LOS/弹道边缘阻挡。
- 旧 `cover_mask` 转换。
- MapDefinition EdgeData 输出。

验收门槛：

- 同一物理边不会重复保存。
- 旋转/移动后两侧方向正确。
- Cover 系统可以只通过 MapDefinition 查询正式边缘数据。

## 阶段 E：内容扩展工具

目标：降低新增地格和批量搭建成本。

内容：

- 新增/复制 Definition 向导。
- 缩略图生成。
- Library binding 管理。
- Rectangle、Fill、Move、Duplicate。
- Stamp 定义和组合模板。
- 收藏、最近使用、标签筛选。

验收门槛：

- 新增一种基于现有 MeshLibrary item 的地格无需修改代码。
- 新元素配置完成后立即进入素材栏并可正常 Bake。
- 房间/楼梯等模板能够作为一次事务放置和撤销。

## 阶段 F：稳定性和生产优化

目标：从可用工具提升为长期内容生产工具。

内容：

- 数据迁移 UI 和 ID alias。
- 大选区性能优化。
- 更稳定的资源差异和错误恢复。
- 自动墙角/变体等按需求增加。
- 使用说明和常见问题。
- Godot 版本升级兼容检查。

# 19. 两个开发任务的分工方式

实际开发继续采用两个现有任务分工，主任务只负责接口规划、进度协调和验收。

## 任务 A：数据、Baker 与迁移

文件所有权：

- `scripts/core/map/**`
- `scripts/map_authoring/tactical_map_baker.gd`
- `scripts/map_authoring/tactical_map_validator.gd`
- `scripts/map_authoring/tactical_map_migrator.gd`
- `resources/map_tiles/**`
- 对应纯逻辑测试

主要职责：

- Resource 数据结构。
- 稳定 ID 和 Library binding。
- Rule merge。
- AuthoringData。
- Baker/Validator V2。
- 兼容迁移。

## 任务 B：编辑器插件与交互

文件所有权：

- `addons/tactical_map_editor/**`
- 插件专用 UI、Gizmo 和 Inspector。

主要职责：

- Dock、素材栏和工具栏。
- 视口拾取、画笔和预览。
- PlacementAdapter 的编辑器实现。
- Undo/Redo。
- 属性面板和调试可视化。

## 接口冻结规则

任务 B 不直接修改任务 A 的核心 Resource 字段；如果接口不足，先提出变更，由主任务确认后交任务 A 修改。任务 A 不进入插件 UI 文件实现交互。

每个阶段按以下顺序推进：

1. 主任务冻结本阶段接口和验收条件。
2. 两个任务在不重叠目录中并行开发。
3. 任务 A 先提供可加载的数据合同或最小 stub。
4. 任务 B 接入正式接口。
5. 主任务检查 Git diff、资源兼容、错误输出和运行结果。
6. 验收通过后再进入下一阶段。

# 20. 测试与验收策略

## 20.1 自动化测试范围

允许并建议测试：

- 稳定 ID 唯一性和 Library 查找。
- item binding 的稳定性。
- CellRules 合并。
- CellOverride mask 继承/覆盖。
- EdgeKey 规范化。
- 边缘旋转、镜像和两侧交换。
- PlacementTransaction 的 do/undo 快照。
- Baker 的固定排序和重复输出一致性。
- 旧 Catalog 到新 Definition 的迁移。
- 无效引用和 schema version 错误。

测试使用内存构造的最小数据，不依赖某一张正式地图的具体布局。

## 20.2 明确不编写的测试

遵循项目要求，不为可持续编辑的地图场景编写以下自动化测试：

- 断言某张地图必须有固定地格数量。
- 断言某个坐标必须是某种模型。
- 断言 prototype 地图的固定装饰布局。
- 因美术调整地图就需要同步修改的场景快照测试。

地图内容正确性由 Validator 和人工编辑验收负责，不把可编辑内容冻结在测试脚本里。

## 20.3 编辑器人工验收

每个阶段至少检查：

- 新建地图和打开现有地图。
- 连续绘制、擦除、吸取、旋转。
- 多楼层切换和上层放置。
- Undo/Redo 多次往返。
- 保存、关闭、重开。
- Validate 错误定位。
- Bake 后运行主场景。
- 单位中心、移动高亮、寻路和鼠标拾取未回归。

## 20.4 性能验收

- 连续画笔不能每格保存一次外部资源。
- 一个 stroke 只创建一个 Undo Action。
- 热力图和 Gizmo 使用批量绘制，不为每格长期创建复杂节点树。
- Baker 只在显式 Validate/Bake 或必要刷新时全量扫描。
- 第一版以 DEMO 小地图稳定流畅为标准；出现真实大地图需求后再引入分块和增量 Bake。

# 21. 完成定义

## 21.1 MVP 完成标准

满足以下条件后，创造模式地编 MVP 完成：

1. 选中 `TacticalMapAuthor` 后自动出现地图编辑 Dock。
2. 使用者可以从统一素材栏选择当前四种基础地格和至少一种对象。
3. 使用者无需手工切换 GridMap 节点即可放置到正确层。
4. Paint、Erase、Pick、Rotate、楼层切换可用。
5. 连续 stroke 可以一次撤销和重做。
6. 保存重开后地图与附加数据一致。
7. Validate/Bake 可以从 Dock 执行。
8. 当前原型地图和运行时流程不发生语义回归。

## 21.2 完整系统完成标准

1. 地格、边缘、对象和模板拥有统一素材栏。
2. 新增一种基于现有资产的地格不需要修改 GDScript。
3. 全局默认属性与单格覆盖均可在编辑器中修改。
4. 行动力、通行、视线、弹道、遮挡高度和掩体可视化可用。
5. 半掩体、全掩体和门能够作为边缘元素放置。
6. 选择、矩形、Fill、移动、复制和 Stamp 工作流可用。
7. 所有数据修改接入 Undo/Redo 和保存提示。
8. Baker 输出固定、可校验、可迁移的运行时资源。
9. 当前地图完成无损迁移。
10. 使用者能够仅阅读使用说明，独立创建一张包含多楼层、Loot、敌人、撤离和掩体的小型地图。

# 22. 风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| GridMap 几何与外部 AuthoringData 不同步 | 所有插件操作经过 PlacementAdapter；Validator 检查 orphan 数据；保存提示覆盖外部资源 |
| MeshLibrary item ID 变化 | 稳定 placeable ID 为权威；Library 持久化 binding；编号不自动复用 |
| 插件和运行时耦合 | 核心 Resource/Baker 放在 `scripts`；运行时不引用 `addons` |
| 多楼层鼠标拾取错误 | 使用当前楼层平面与物理命中结合；禁止固定投影到 Y=0 |
| Undo/Redo 数据不完整 | stroke 前捕获全部受影响几何、覆盖、边缘和 Marker 快照 |
| 旋转后掩体方向错误 | EdgeKey 规范化和方向变换只有一套正式实现，并进行纯逻辑测试 |
| 大量节点导致编辑器变慢 | 规则格继续使用 GridMap；边缘预览使用批量 Gizmo/MultiMesh；不把每格变成独立 Node |
| `.tscn` 地图产生 Git 冲突 | 一张地图明确一个编辑负责人；定义一文件一个；数组固定排序；后续真实需要时再按楼层/区域分块 |
| Godot 4.7 EditorDock API 变化 | UI 注册封装在 Dock Host；项目固定 Godot 4.7 开发基线；升级时集中适配 |
| 过度设计拖慢玩法 | 按阶段交付；Stamp、自动墙角和大地图分块不进入 MVP |

# 23. 最终决策摘要

1. 地编系统的外部形态是 Godot `EditorPlugin`。
2. 插件只负责创造模式工作流，不承载核心地图规则。
3. 底层继续使用 GridMap，不重新实现体素渲染和物理系统。
4. 地格/元素使用稳定 ID 的 Resource 定义，MeshLibrary 数字 ID 仅为内部适配。
5. GridMap 保存规则网格表现；AuthoringData 保存单格覆盖和边缘；Marker 保存独立对象。
6. Baker 合并默认规则、结构贡献和实例覆盖，生成唯一运行时地图合同。
7. 掩体、门等采用正式 Edge 数据，不长期依赖整格 `cover_mask`。
8. 所有编辑操作必须支持 Undo/Redo、保存提示和可视化校验。
9. 当前地图通过兼容层渐进迁移，不重画、不推翻运行时系统。
10. 开发先完成数据基础和插件 MVP，再完成属性可视化与边缘系统，最后接正式掩体玩法和高级内容工具。

最终目标不是复制 MC 的体素世界，而是获得其“选择内容、直接放置、立即反馈、容易扩展”的创造模式体验，同时保持战术游戏所需的明确地格规则、可验证数据和稳定运行时合同。

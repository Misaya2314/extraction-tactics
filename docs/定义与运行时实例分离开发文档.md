# 1. 文档目的

本文件定义项目“定义与运行时实例分离”的正式开发架构、数据合同、迁移顺序、测试策略和验收标准。

本系统不是为了形式上增加更多类，而是解决以下实际问题：

- 同一种物品需要存在多个彼此独立的个体。
- 同型号武器未来需要分别保存弹药、耐久、配件和随机属性。
- 同一单位模板需要生成多个拥有不同生命、行动点、装备和位置的单位。
- 同一张地图需要重复开局，但每局的占用、Loot、环境对象状态不能污染地图资源。
- 运行中的单位和对象不能因为场景节点销毁、切换或重建而丢失关键状态。
- 撤离结算、基地仓库和存档必须能够准确识别并恢复“同一件具体物品”。
- 后续环境交互系统需要保存爆炸桶、门、机关、危险区域等对象的当前状态。

本系统建立以下统一关系：

```text
Definition
描述“一类内容是什么”
        ↓
Runtime Instance / Runtime State
描述“这一局中的这个具体对象现在怎样”
        ↓
Placement / Ownership
描述“它当前在哪里、属于谁”
        ↓
Snapshot
描述“如何保存并重建这些状态”
        ↓
Scene View / UI
负责显示运行时权威状态
```

开发必须遵循《通用开发规则文档》中的：

- 数据驱动优先。
- 单一规则来源。
- 表现层不决定规则。
- 静态配置与运行时状态分离。
- 新系统必须考虑存档与重建。
- 保持简单，为已知变化设计。

# 2. 核心决策摘要

本系统采用以下正式决策：

1. Godot `.tres` Definition 在运行时视为只读共享模板。
2. 每个需要独立状态或身份的具体对象使用 Runtime Instance 表达。
3. Scene Node 不是正式的运行时状态本体，只是状态的 View 或 Adapter。
4. 地图中的 `MapSpawnData`、`MapObjectPlacement` 是生成/放置说明，不等于本局实例。
5. 物品所在容器、背包坐标和旋转属于 Placement，不属于物品 Definition。
6. 所有运行时实例使用稳定 `instance_id`，禁止将 Godot `Object.get_instance_id()` 用作存档身份。
7. Definition 通过“类型 + 稳定 ID”解析；存档不以资源路径作为唯一合同。
8. 运行时创建必须经过领域 Factory 和统一 ID 服务，不允许各系统自行拼接可能冲突的 ID。
9. Snapshot 只保存恢复所需的权威状态，不保存可以由 Definition 或其他状态推导的数据。
10. Grid 占用、动态阻挡、UI 文本和 3D Transform 属于派生状态，恢复时重新构建。
11. 当前正确实现渐进迁移，不推翻 Item、Loot、Grid 已有逻辑。
12. 首轮只建立当前已知需求需要的状态字段，不提前实现弹药、耐久、随机词条等未进入玩法的内容。

# 3. 范围与非目标

## 3.1 本系统范围

本系统完整目标包括：

- Definition 身份与统一查找。
- Runtime Instance 身份与生命周期。
- 运行时实例 ID 生成与唯一性校验。
- Runtime Registry。
- Definition、Instance、Placement、Snapshot 的职责边界。
- Item、Loot、Weapon、Unit、Map、Environment、Session 的目标结构。
- 运行时状态与 Node3D/UI 的绑定方式。
- Snapshot 创建、验证、保存、加载和迁移合同。
- 现有系统的兼容迁移。
- 纯逻辑自动化测试和调试诊断。

## 3.2 首轮实现范围

首轮开发优先完成：

- Definition Key 与显式 Content Manifest。
- 统一 Definition Registry 和重复/缺失 ID 诊断。
- 统一运行时实例 ID 生成器。
- 最小 Runtime Instance 身份合同。
- Item Instance、Inventory Placement、Loot Container 的身份和快照闭环。
- Unit Runtime State 与 `PrototypeUnit` View 的基础分离。
- Weapon Instance 的最小合同或兼容入口。
- Raid Session Snapshot 的基础结构与内存往返恢复。
- 功能测试。

## 3.3 本阶段非目标

本阶段不要求：

- 完整基地玩法和基地 UI。
- 正式存档槽界面、云存档或存档加密。
- 弹药、耐久、枪械配件、随机词条的具体玩法。
- 完整环境交互、爆炸、推动和地形杀。
- 网络同步、回滚网络或多人 ECS。
- 将所有 Godot Node 一次性删除或替换。
- 建立一个能够容纳所有未知状态的通用属性字典。
- 为具体可编辑地图内容编写自动化地图测试。

上述内容可以使用本系统提供的接口继续开发，但不得反向扩大首轮交付范围。

# 4. 术语

| 术语 | 含义 |
| --- | --- |
| Definition | 一类内容共享的静态配置，通常是 `.tres` Resource |
| Definition Key | 由 `definition_type + definition_id` 组成的稳定内容身份 |
| Runtime Instance | 一局或一个存档中存在的具体对象，具有唯一 `instance_id` |
| Runtime State | 具体实例当前可变化的权威状态 |
| Placement | 实例在某个空间或容器中的位置、方向、占格和所属关系 |
| Ownership | 哪个容器、单位、地图或存档当前拥有某个实例 |
| Snapshot | 用于保存、复制、传输和重建运行时状态的数据快照 |
| Registry | 通过稳定 ID 查找 Definition 或 Runtime Instance 的索引服务 |
| Factory | 创建或从 Snapshot 恢复实例的唯一正式入口 |
| View | Node3D、Control、动画、特效等表现对象 |
| Authoring Placement | 地图编辑器保存的生成点或对象放置说明 |
| Derived State | 可以根据权威状态重新计算的数据，例如 Grid 占用、UI 文本和可走高亮 |

## 4.1 Definition 不等于场景节点

一个 `.tscn` 可以是表现模板，但实例化出的 Node 仍不自动成为正式 Runtime Instance。

以下代码生成了 Godot 对象：

```gdscript
var node := scene.instantiate()
```

但它没有自动解决：

- 稳定身份。
- 独立运行时状态。
- 存档恢复。
- 跨场景存活。
- 所有权和位置关系。

因此正式状态不能只依赖 Node 是否存在。

## 4.2 Authoring Placement 不等于 Runtime Instance

例如：

```text
MapSpawnData
    描述“这个生成点可以生成什么”

UnitRuntimeState
    描述“本局实际生成出来的这个单位怎样”
```

同一个生成点在不同战局中可以生成不同单位；随机生成系统也可能在一个候选组中只选择部分点位。因此生成点 ID 和单位实例 ID 必须分开。

# 5. 必须保持的系统不变量

以下规则属于系统硬约束。

## 5.1 Definition 运行时只读

运行时代码不得为了保存个体状态而修改共享 Definition：

```gdscript
# 禁止
weapon_definition.damage -= 1
item_definition.value = runtime_value
unit_archetype.max_hp = current_hp
```

Godot `ResourceLoader` 会缓存 Resource。同一 `.tres` 很可能被多个对象共享，修改一个引用可能同时改变所有使用者，并污染后续逻辑或编辑器状态。

## 5.2 Instance 身份唯一且稳定

- 同一运行时作用域内不能存在重复 `instance_id`。
- 实例在容器之间转移时保持同一 ID。
- 保存和加载后保持同一 ID。
- Node 被销毁并重新创建后保持同一 ID。
- ID 不允许依赖数组下标、当前 Node 路径或 `get_instance_id()`。

## 5.3 一个状态只有一个权威来源

不能长期同时在多个位置维护同一个状态。

例如物品旋转目前同时存在于：

- `InventoryItemInstance.rotation`。
- `InventoryItemPlacement.rotation`。

目标架构规定：

> 背包中的朝向属于 Placement，`InventoryItemPlacement.rotation` 为权威来源。

Instance 上的旋转字段进入兼容迁移，最终不再作为正式状态来源。

同理：

- 单位当前位置由 `UnitRuntimeState.cell` 权威保存。
- Grid Occupancy 根据单位状态同步构建。
- Node3D `global_position` 只是表现结果。

## 5.4 一个实例只能有一个有效位置/所有者

一个物品不能同时：

- 在 Loot 容器中；
- 在小队背包中；
- 被单位装备；
- 作为地图掉落物存在。

转移操作必须是事务：旧位置成功移除且新位置成功接收后才算完成；失败时恢复原状态。

## 5.5 Snapshot 不保存派生数据

可以重新计算的内容不进入权威 Snapshot，例如：

- UI Label 文本。
- 3D Node Transform。
- 当前高亮格。
- 路径搜索缓存。
- Grid 的可达区域缓存。
- 根据对象状态派生的动态阻挡结果。

保存源状态，加载后统一重建派生结果。

## 5.6 View 不直接创造规则状态

View 可以：

- 转发输入意图。
- 显示生命、AP、物品和环境状态。
- 播放动画、Tween、VFX 和音效。

View 不应：

- 独立决定伤害。
- 自行生成正式实例 ID。
- 仅通过 `queue_free()` 决定对象在规则上已经销毁。
- 把动画播放进度作为战局权威状态。

# 6. 当前项目现状

## 6.1 总体评估

当前项目不是从零开始。物品、Loot 和地图已经存在正确的分离基础；单位、武器、Session 和环境对象需要补齐统一合同。

| 领域 | Definition / 静态合同 | 当前 Runtime | 当前评价 |
| --- | --- | --- | --- |
| 物品 | `ItemDefinition` | `InventoryItemInstance` | 基础分离正确，状态和 ID 机制仍薄 |
| 背包 | Definition 中的形状 | `InventoryItemPlacement`、`SquadInventory` | 三层结构正确，旋转权威来源需收口 |
| Loot | `LootTableDefinition` | `LootContainerModel` | 能由定义生成独立实例，ID 和 Snapshot 需统一 |
| 武器 | `WeaponDefinition` | 单位直接持有 Definition | 尚无具体武器实例 |
| 单位 | `UnitArchetype`、`MapSpawnData` | `PrototypeUnit` Node3D | 部分分离，关键状态绑定 Node |
| 地图 | `TacticalMapDefinition` | `GridModel` | 分离良好，动态覆盖和 Snapshot 尚未形成 |
| 环境对象 | `TacticalObjectDefinition`、`MapObjectPlacement` | 无正式 State | 已声明方向，但运行时层缺失 |
| 战局 | Map、Spawn、Loot 等 Definition | `GameStateManager` 和 Controller 中的零散状态 | 缺少统一 Session State 聚合 |
| AI | 巡逻路线、单位 Definition | `AlertState` 和 Controller 字典 | 运行状态存在，但尚无统一身份/快照 |

## 6.2 已经正确的部分

### 物品三层结构

当前已经形成：

```text
ItemDefinition
    ↓
InventoryItemInstance
    ↓
InventoryItemPlacement
```

这应作为其他领域的参考实现，而不是推翻。

### Loot 从 Definition 生成实例

`LootTableDefinition.generate_contents()` 返回物品定义，`LootContainerModel.initialize()` 再创建不同 `InventoryItemInstance`。同一种物品被抽中多次时能够产生不同实例。

### 地图定义与 GridModel 分离

`TacticalMapDefinition` 是 Baker 生成的只读地图合同；`GridModel` 加载后维护本局占用和查询状态。同一张地图可以重复创建多个运行时 Grid。

## 6.3 需要解决的具体问题

### 物品实例 ID 由各容器局部生成

当前 `SquadInventory` 和 `LootContainerModel` 各自生成 ID。它们在局部范围内可用，但无法保证：

- 跨多个容器全局唯一。
- 撤离进入基地后仍稳定。
- 存档加载后不与新生成物品冲突。

### `InventoryItemInstance.copy()` 语义不清

当前 `copy()` 保留原 `instance_id`。这可能表示：

- 同一个实例的快照副本；或
- 新建一个相同物品。

两种含义完全不同。目标架构必须拆成明确接口：

```text
to_snapshot()                保存同一实例
restore_from_snapshot()      恢复同一实例
clone_as_new(new_id)         创建新的独立实例
```

### 物品旋转重复保存

`InventoryItemInstance` 和 `InventoryItemPlacement` 同时保存旋转。需要让 Placement 成为唯一权威来源，并提供兼容代理直到 UI 完成迁移。

### 单位状态绑定 Node3D

`PrototypeUnit` 当前同时保存：

- `current_hp`。
- `current_action_points`。
- `grid_cell`。
- `facing`。
- `unit_id`。
- Definition 引用。
- 武器数据代理。
- 动画和模型状态。

这使得销毁或重建 Node 时必须人工复制状态，也无法在不加载 3D 场景的情况下完整恢复单位。

### 单位 ID 使用 Godot 实例 ID

`PrototypeUnit` 当前通过 `get_instance_id()` 拼接 `unit_id`。该值只在当前进程和当前对象生命周期内有效，不能作为存档、回放或跨场景身份。

### 武器只有 Definition

目前固定伤害、射程和 AP 可以直接使用 `WeaponDefinition`。但后续弹药、耐久、配件、品质和撤离携带需要 `WeaponInstance`。

### 地图对象缺少运行时状态

`TacticalObjectDefinition` 已说明 Runtime State 应保存在 Session，但当前没有对应的正式 `EnvironmentObjectState` 或 `MapObjectRuntimeState`。

### Session 只保存阶段和结果

`GameStateManager` 是清晰的状态机，但它不应扩展成保存全部单位、物品、地图和环境状态的巨型对象。需要单独的 `RaidSessionState` 聚合运行时数据。

# 7. 目标架构

```text
GameContentManifest
        ↓
GameDefinitionRegistry
        ↓ resolve(type, id)
┌──────────────────────────────────────┐
│ Definitions                         │
│ Item / Weapon / Unit / Map / Object │
└──────────────────────────────────────┘
        ↓ Factory 创建
┌──────────────────────────────────────┐
│ Runtime Instances / States           │
│ Item / Weapon / Unit / Environment   │
└──────────────────────────────────────┘
        ↓ register / ownership
RuntimeInstanceRegistry
        ↓
RaidSessionState
        ├── Inventories / Containers / Equipment
        ├── Unit States
        ├── Environment States
        ├── Map Runtime State
        └── Phase / Turn / Random Seed
        ↓
Snapshot DTO → Codec → user:// Save
        ↓ restore
Scene Factory / View Binder → Node3D / UI
```

## 7.1 分层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Definition | 基础配置、表现资源引用、共享规则参数 | 当前 HP、当前位置、是否打开 |
| Placement | 作者位置、容器位置、方向和占格 | 物品固有状态、战局结算 |
| Runtime State | 当前可变状态、稳定实例身份 | 3D 动画、编辑器数据 |
| Registry | 唯一性、查找、引用恢复 | 具体战斗规则 |
| Session | 聚合并管理本局状态和生命周期 | Definition 编辑 |
| Snapshot | 可序列化的权威状态 | Node、Texture、Callable、缓存 |
| View | 显示、动画、输入转发 | 最终规则计算和存档身份 |

# 8. Definition 合同

## 8.1 Definition Key

所有 Definition 必须能够提供：

```text
definition_type
definition_id
```

例如：

```text
item / medkit
weapon / shotgun
unit_archetype / rifleman
map / prototype_map
placeable / prototype_explosive_barrel
cover / cover_half
```

ID 在自己的类型命名空间内唯一。存档必须同时保存类型和 ID，不能只保存 `medkit` 这样的裸字符串并假设全项目不冲突。

## 8.2 兼容现有字段

现有资源已经分别使用：

- `item_id`。
- `weapon_id`。
- `archetype_id`。
- `map_id`。
- `placeable_id`。
- `cover_id`。

首轮不要求立即统一重命名字段。每种 Definition 只需要提供统一协议：

```gdscript
func get_definition_type() -> StringName
func get_definition_id() -> StringName
func is_valid() -> bool
```

如果后续多个 Definition 出现大量重复实现，再考虑引入极薄的 `GameDefinition` 基类。首轮不为了形式统一强制重写全部继承树。

## 8.3 Definition 允许保存的内容

- 稳定 ID。
- 显示名称。
- 图标、模型和表现 Profile。
- 基础属性和规则参数。
- 标签和分类。
- 形状、默认武器、默认效果等静态引用。
- Definition 自身 schema version（真正需要独立迁移时）。

## 8.4 Definition 禁止保存的内容

- 当前 HP/AP。
- 当前弹药和耐久。
- 当前所在格或背包坐标。
- 当前拥有者。
- 是否已打开、已拾取或已销毁。
- 本局随机结果。
- Node、RID、Callable 和场景树引用。

## 8.5 Definition 引用策略

作者数据中继续允许使用强类型 Resource 引用，方便 Godot Inspector 和 ResourceTables 编辑，例如：

```gdscript
@export var weapon: WeaponDefinition
```

运行时状态可以缓存已解析的 Definition 引用以提高使用便利性，但 Snapshot 只保存 Definition Key。

禁止将以下内容作为长期存档的唯一引用：

- `res://...` 路径。
- Resource UID。
- 数组下标。
- MeshLibrary item ID。

这些可以作为诊断或适配信息，但稳定 Definition ID 才是正式内容合同。

# 9. GameContentManifest 与 Definition Registry

## 9.1 为什么需要显式 Manifest

保存只记录 Definition Key，加载时必须能够稳定找到对应 Resource。

不建议运行时递归扫描 `resources/**`：

- 导出包中的文件枚举行为可能不同。
- 资源目录重构会改变结果。
- 重复 ID 和遗漏引用难以及早发现。
- 加载顺序不明确。

建议增加显式：

```text
GameContentManifest
    item_definitions
    weapon_definitions
    unit_archetypes
    map_definitions
    placeable_definitions
    cover_profiles
```

资源建议位于：

```text
resources/content/game_content_manifest.tres
```

## 9.2 GameDefinitionRegistry

Registry 在游戏启动或战局创建前由 Manifest 配置，提供：

```gdscript
configure(manifest) -> ValidationResult
resolve(definition_type, definition_id) -> Resource
contains(definition_type, definition_id) -> bool
get_all(definition_type) -> Array[Resource]
validate() -> Array[Diagnostic]
```

Registry 配置完成后运行时只读。

## 9.3 必须检查的问题

- 同类型重复 ID。
- 空 ID。
- 无效 Definition。
- Manifest 中空引用。
- Definition 引用了 Manifest 中不存在的其他 Definition。
- ID alias 循环。
- 已删除 Definition 导致 Snapshot 无法解析。

## 9.4 ID 改名与删除

Definition ID 是存档合同，不能静默改名。

建议 Manifest 或独立迁移表支持：

```text
old_definition_key → new_definition_key
```

加载顺序：

1. 尝试直接解析当前 ID。
2. 查找 alias/migration。
3. 解析迁移后的 ID。
4. 仍缺失则返回明确错误，不静默换成默认物品。

# 10. Runtime Instance 基础合同

## 10.1 RuntimeInstance 基类

建议增加一个极薄的基类：

```gdscript
class_name RuntimeInstance
extends RefCounted

var instance_id: StringName
var definition_type: StringName
var definition_id: StringName
```

基类只负责身份和通用验证，不负责：

- 生命。
- 物品属性。
- 装备。
- 地图位置。
- 环境反应。

具体领域继续使用自己的类型：

```text
InventoryItemInstance
WeaponInstance
UnitRuntimeState
EnvironmentObjectState
```

如果实际迁移发现继承影响现有类型，可先采用同名方法协议，再在后续收敛为基类；身份合同优先于继承形式。

## 10.2 Runtime Instance 最小接口

```gdscript
func is_valid(registry: GameDefinitionRegistry) -> bool
func get_stable_instance_id() -> StringName
func get_definition_key() -> DefinitionKey
func to_snapshot() -> RuntimeSnapshot
```

Godot 的 `Object` 已原生提供 `get_instance_id() -> int`。该原生方法只表示当前进程中的对象身份，不能覆盖成稳定字符串，也不能用于存档合同；因此本系统统一通过 `instance_id` 字段或 `get_stable_instance_id()` 读取可持久化身份。

实例不得通过修改 Definition 实现状态变化。

## 10.3 RuntimeInstanceRegistry

运行时 Registry 负责：

- 注册实例。
- 拒绝重复 ID。
- 根据 ID 查询实例。
- 记录实例类型。
- 在实例销毁或离开作用域时注销。
- 为 Snapshot 恢复进行交叉引用解析。

Registry 是索引和唯一性守卫，不应成为所有领域状态的巨型所有者。

实际所有权仍由：

- Raid Session。
- Inventory / Loot Container。
- Unit Equipment。
- Map Runtime。

按照领域规则管理。

# 11. 运行时实例 ID 方案

## 11.1 ID 类型

必须区分：

| ID | 用途 |
| --- | --- |
| Definition ID | 表示内容类型，例如 `medkit` |
| Placement ID | 表示作者地图上的点位，例如 `warehouse_barrel_03` |
| Instance ID | 表示本局或存档中的具体对象 |
| Session ID | 表示一次战局 |
| Save ID | 表示一个存档记录 |

这些 ID 不允许混用。

## 11.2 InstanceIdGenerator

建议由 `InstanceIdGenerator` 统一生成：

```gdscript
next_id(instance_type: StringName) -> StringName
id_for_placement(instance_type, map_id, placement_id) -> StringName
```

推荐可读格式：

```text
<session_id>:item:000001
<session_id>:unit:000003
<session_id>:environment:prototype_map:barrel_03
```

业务代码不解析 ID 字符串；格式只用于诊断。

## 11.3 两种生成方式

### 作者点位生成

地图中明确存在的对象或固定单位，可由以下信息确定性生成：

```text
session_id + map_id + placement_id
```

这样加载同一战局时可以恢复同一实例。

### 动态生成

Loot、随机敌人、运行时召唤物等使用 Session 内计数器或等价的稳定生成方式。

## 11.4 跨战局持久实例

成功撤离进入基地的物品继续保留原 `instance_id`，不因进入新容器而换 ID。

从基地携带进下一局时仍是同一件物品。新战局生成器必须接受已有 ID 集合，并保证新 ID 不冲突。

## 11.5 禁止的 ID 来源

- `Node.get_instance_id()`。
- NodePath。
- 当前数组下标。
- 显示名称。
- 仅使用 `container_id + item_index` 且不包含 Session 身份。
- 随机生成但不保存的临时值。

# 12. Placement 与 Ownership

## 12.1 物品 Placement

目标结构：

```text
InventoryItemInstance
    instance_id
    definition_id
    固有可变状态

InventoryItemPlacement
    instance_id / instance reference
    container_id
    anchor
    rotation
```

`rotation` 属于 Placement，因为它描述物品在当前格子容器中的摆放方式。

## 12.2 单位 Placement

单位当前位置是战局状态的重要组成部分，建议由 `UnitRuntimeState.cell` 保存。

GridModel 的 Occupancy 是根据所有单位 State 建立的运行时索引，不是第二份独立真相。

强制移动或普通移动流程：

1. 验证目标位置。
2. 原子更新 Unit State 和 Grid Occupancy。
3. 成功后通知 View 播放移动表现。
4. 失败时保持两者原状态。

## 12.3 环境对象 Placement

地图作者保存：

```text
MapObjectPlacement
    placement_id/object_id
    definition
    cell
    facing
    instance_overrides
```

战局创建：

```text
EnvironmentObjectState
    instance_id
    placement_id
    definition_id
    current_state
    current_hp
    cell
    facing
```

## 12.4 所有权事务

物品转移接口必须保证：

```text
validate source
→ validate destination
→ reserve destination
→ remove source
→ commit destination
→ update location index
```

任何步骤失败都不得产生物品复制或丢失。

# 13. Snapshot 与持久化合同

## 13.1 Snapshot 的定位

Runtime Instance 是游戏运行对象；Snapshot 是可序列化 DTO。两者职责不同。

不建议直接把所有 Runtime Instance 改成 `.tres` 并原样保存，因为运行对象可能包含：

- 缓存的 Definition 引用。
- Signal。
- Runtime Registry 引用。
- 临时索引。
- 不应该持久化的派生状态。

## 13.2 Snapshot 必须只包含基础可序列化值

允许：

- `bool/int/float/String/StringName`。
- `Vector2i/Vector3i` 的明确编码。
- Array、Dictionary 中的基础值。
- 其他 Snapshot。

禁止：

- Node。
- Resource Definition 直接引用。
- Texture、PackedScene。
- Callable、Signal、RID。
- Godot Object instance ID。

## 13.3 建议 Snapshot 类型

```text
ItemInstanceSnapshot
ItemPlacementSnapshot
WeaponInstanceSnapshot
UnitStateSnapshot
EnvironmentObjectSnapshot
LootContainerSnapshot
InventorySnapshot
RaidSessionSnapshot
ProfileSnapshot
SaveGameSnapshot
```

Snapshot 在内存中可以使用类型化 `RefCounted` DTO；Codec 再转换为 Dictionary 并写入 `user://`。这样既便于测试，也避免领域逻辑直接依赖文件格式。

## 13.4 根存档结构

建议：

```text
SaveGameSnapshot
    schema_version
    content_version
    save_id
    profile_id
    created_at
    profile_snapshot
    active_raid_snapshot（可选）
```

### ProfileSnapshot

用于跨局长期存在的状态：

- 基地仓库物品。
- 长期单位。
- 进度、货币和解锁内容。

### RaidSessionSnapshot

用于一次战局：

- `session_id`。
- 地图 Definition ID。
- 随机种子和必要计数器。
- 战局阶段和回合。
- 单位状态。
- Loot 容器状态。
- 环境对象状态。
- 本局背包和装备。

## 13.5 各领域快照建议

### ItemInstanceSnapshot

```text
instance_id
definition_id
state_version
```

当前只保存真实存在的状态。未来需要时再增加：

- `stack_count`。
- `durability`。
- `identified`。
- 随机 Modifier ID。

### ItemPlacementSnapshot

```text
instance_id
container_id
anchor
rotation
```

### WeaponInstanceSnapshot

```text
instance_id
definition_id
state_version
```

未来扩展：

- 当前弹药。
- 耐久。
- 配件实例 ID。
- 改装状态。

### UnitStateSnapshot

```text
instance_id
archetype_id
faction
current_hp
current_action_points
cell
facing
weapon_instance_id
inventory_id
alive
```

### LootContainerSnapshot

```text
instance_id/container_id
placement_id
opened
depleted
contained_item_ids
```

### EnvironmentObjectSnapshot

```text
instance_id
placement_id
definition_id
cell
facing
state
current_hp
enabled
```

## 13.6 不保存派生 Grid 状态

以下内容优先通过 Unit、Environment 和 Map Definition 恢复：

- 单位占用字典。
- 环境动态阻挡索引。
- 当前可达格缓存。
- LOS 缓存。
- Cover Query 缓存。

如果后续出现无法可靠推导的运行时地图改造，再增加正式 `MapRuntimeMutationSnapshot`，而不是提前保存整个 GridModel 内部字典。

## 13.7 内容版本策略

Snapshot 保存 `content_version`。

DEMO 阶段默认采用：

> Definition 使用加载时最新配置，Snapshot 只恢复个体状态。

因此修改武器基础伤害会影响旧存档中的同型号武器。这符合当前快速迭代需求。

未来如果需要版本锁定或赛季规则，应另行增加 Definition 版本或数据迁移，首轮不复制整份 Definition 到存档。

# 14. 保存与恢复流程

## 14.1 保存流程

```text
请求保存
→ 冻结当前规则事务
→ 校验 Runtime Registry 和 Ownership
→ 各领域生成 Snapshot
→ 聚合为 Raid/Profile Snapshot
→ Snapshot Validator
→ Codec 编码
→ 写临时文件
→ 成功后替换正式存档
```

保存失败不能覆盖上一份有效存档。

## 14.2 恢复顺序

恢复必须按依赖顺序执行：

1. 读取并校验 Snapshot schema。
2. 加载 GameContentManifest。
3. 构建 Definition Registry。
4. 解析地图 Definition。
5. 创建空 RaidSessionState 和 Runtime Registry。
6. 创建全部 Item、Weapon、Unit、Environment 实例，但暂不触发玩法事件。
7. 注册全部实例并解析交叉引用。
8. 恢复 Inventory、Loot Container、Equipment 等所有权关系。
9. 根据 Map Definition 创建 GridModel。
10. 根据单位和环境状态重建 Occupancy、动态阻挡和 Edge Overlay。
11. 创建并绑定 3D View。
12. 批量刷新 UI、可见性、掩体和 AI。
13. 恢复正常事件派发。

## 14.3 Hydration 期间禁止副作用

恢复 `current_hp = 0` 时不能再次触发：

- 死亡奖励。
- 爆炸。
- Loot 掉落。
- 任务计数。
- AI 警报。

建议提供明确恢复模式或静默赋值接口，恢复完成后再统一发布 `session_restored`。

# 15. 各领域目标结构

## 15.1 物品与背包

### 保留

- `ItemDefinition`。
- `InventoryItemInstance`。
- `InventoryItemPlacement`。
- `SquadInventory` 的格子放置算法。

### 调整

- `InventoryItemInstance` 接入统一身份合同。
- Instance 创建改由 `ItemInstanceFactory` 和统一 ID 生成器负责。
- Placement 成为旋转权威来源。
- `SquadInventory._next_instance_id` 仅作为兼容路径，最终移除。
- `copy()` 标记废弃，替换为 Snapshot 和显式 Clone。
- Inventory 增加 `inventory_id`。
- 增加 Item、Placement、Inventory Snapshot。

### 不提前增加

- 耐久。
- 堆叠。
- 品质。
- 随机词条。

这些字段在具体玩法进入开发时增加，不为了填满架构预先实现。

## 15.2 Loot

目标链路：

```text
LootTableDefinition
    ↓ Roll，仅产生 Definition 选择结果
ItemInstanceFactory
    ↓ 生成唯一实例
LootContainerState
    ↓ 保存打开/耗尽和物品所有权
Inventory Transfer
```

调整内容：

- `LootContainerModel` 使用外部 ID Generator。
- Container 保存/恢复 contained item IDs。
- 物品离开 Container 后保持原实例 ID 和状态。
- `LootSettlement` 生成 Snapshot，不通过含糊 `copy()` 复制运行时对象。
- 成功撤离把同一实例移交 Profile/Stash；失败按正式规则销毁或保留安全区物品。

## 15.3 武器

目标结构：

```text
WeaponDefinition
    基础伤害、射程、AP、模型、反馈
        ↓
WeaponInstance
    具体武器身份和个体状态
        ↓
EquipmentPlacement / UnitRuntimeState
    当前装备关系
```

在没有弹药、耐久和配件的阶段，`WeaponInstance` 可以只有：

```text
instance_id
definition_id
```

但必须明确兼容策略：

- 地图 Spawn 仍可引用 `WeaponDefinition` 作为初始装备模板。
- Unit Factory 根据模板创建 Weapon Instance。
- `PrototypeUnit.weapon` 在迁移期可以继续提供 Definition 代理。
- 新的运行时装备关系以 `weapon_instance_id` 为权威。

## 15.4 单位

目标结构：

```text
UnitArchetype
        ↓
UnitRuntimeState
        ↓
PrototypeUnit / UnitView
```

### UnitArchetype 保存

- 基础最大 HP/AP。
- 移动、视野等基础属性。
- 默认武器 Definition。
- 静态表现配置。

### UnitRuntimeState 保存

- `instance_id`。
- `archetype_id`。
- 阵营。
- 当前 HP/AP。
- 当前格。
- 当前装备实例 ID。
- 生存状态。
- 需要跨场景保留的 AI/状态效果。

### PrototypeUnit 保存

- Node 引用。
- 模型和武器挂点。
- 动画/Tween。
- 选择、状态标签和表现 Signal。
- 对 State 的只读代理和输入转发。

### 迁移兼容

第一阶段允许 `PrototypeUnit.current_hp` 等属性代理到 State，避免一次性修改所有调用者。完成迁移后 Node 不再独立保存第二份 HP/AP/Cell。

`MapSpawnData` 建议增加稳定 `spawn_id`；`unit_name` 继续作为显示名称或兼容字段，不作为实例身份。

## 15.5 地图与 Grid

保留：

```text
TacticalMapDefinition → GridModel
```

进一步明确：

- TacticalMapDefinition 是地图静态/烘焙 Definition。
- GridModel 是本局逻辑索引和查询模型。
- RaidSessionState 保存导致 Grid 变化的源状态。
- GridModel 在加载时由 Map Definition 和源状态重建。

后续环境系统需要增加来源可追踪的动态覆盖：

```text
base cell/edge rules
+ dynamic blockers by source instance ID
= effective Grid query
```

不能通过简单 `set_walkable(true)` 擦除基础地图规则。

## 15.6 环境对象

本系统只建立环境实例基础，不在本阶段完成爆炸玩法。

目标结构：

```text
TacticalObjectDefinition
        ↓ MapObjectPlacement
EnvironmentObjectState
        ↓
EnvironmentObjectView
```

`TacticalObjectDefinition` 保存类型配置；`MapObjectPlacement` 保存作者点位；`EnvironmentObjectState` 保存本局当前状态。

后续爆炸桶、门、陷阱和推动对象都使用这一实例层，不把生命或开关状态写入 `.tres` 或只写在场景节点中。

## 15.7 Session

建议新增：

```text
RaidSessionState
```

它负责聚合：

- Session ID。
- Map Definition ID。
- Definition Registry 引用。
- Runtime Registry。
- Unit States。
- Environment States。
- Inventories 和 Loot Containers。
- 随机种子和 ID Generator 状态。
- GameStateManager。
- TurnManager 所需的可恢复状态。

`GameStateManager` 继续只负责合法阶段和结果状态机，不扩展为全部游戏数据的万能容器。

## 15.8 AI 状态

AI Definition 和运行状态同样分离：

- 巡逻路线、感知基础参数属于 Definition/地图数据。
- 当前警戒阶段、目标实例 ID、最后已知格属于 Unit/Encounter Runtime State。
- AI 不保存目标 Node 引用作为持久合同，只保存目标实例 ID。

首轮只迁移真正需要跨 Node 重建的状态，不要求保存行为树内部每一个临时栈帧。

# 16. Runtime State 与 View 绑定

## 16.1 单向数据关系

推荐：

```text
Runtime State
    ↓ signal / explicit refresh
View
```

输入方向：

```text
View/Input
    ↓ ActionRequest / Command
Controller / Domain Service
    ↓ validation + mutation
Runtime State
```

View 不直接修改自身显示值并假设规则已经成功。

## 16.2 View Binder

单位和环境对象建议分别提供绑定入口：

```gdscript
unit_view.bind_state(unit_state)
environment_view.bind_state(environment_state)
```

绑定后：

- 初始刷新全部表现。
- 订阅正式状态变化。
- View 退出树时断开连接。
- State 不持有强 Node 引用，避免场景释放后留下无效依赖。

## 16.3 动画与规则完成顺序

默认顺序：

1. 验证行动。
2. 提交权威状态。
3. 得到 ActionResult/Event。
4. 播放表现。
5. 表现结束后解锁下一输入。

动画被中断不能回滚已经完成的权威伤害或移动，除非该行动明确采用预提交事务。

# 17. 创建、转移、销毁生命周期

## 17.1 创建

```text
Definition Key / Authoring Placement
→ Factory 解析 Definition
→ ID Generator 分配实例 ID
→ 构造 Runtime State
→ Registry 注册
→ 所有权/位置登记
→ 创建并绑定 View（如果需要）
```

## 17.2 转移

```text
验证来源拥有实例
→ 验证目标可接收
→ 原子修改 Ownership/Placement
→ 实例 ID 和固有状态保持不变
→ 刷新 UI/View
```

## 17.3 销毁

“销毁”必须区分：

- 规则上已销毁。
- 从当前容器移除。
- 从 Registry 注销。
- View 播放销毁表现。
- Node 最终 `queue_free()`。

对需要保存“已经被破坏”的地图对象，规则状态应保留为 `destroyed`，而不是立即从所有记录中完全删除。

# 18. API 与错误合同

## 18.1 不使用静默回退

以下问题必须返回明确诊断：

- Definition 不存在。
- Snapshot schema 不支持。
- 重复 instance ID。
- 同一物品被两个容器拥有。
- Placement 引用了不存在实例。
- Unit 装备了不存在的 Weapon Instance。
- 地图对象 Placement 缺少 Definition。

不得静默创建默认医疗包、默认步枪或默认单位掩盖坏数据。

## 18.2 结果类型

创建、恢复和转移等可能失败的操作，建议返回稳定结果：

```text
success
reason_code
message
related_id
metadata
```

错误代码用于测试和逻辑，文本用于日志和 UI。

## 18.3 事务边界

以下操作必须整体成功或整体失败：

- 物品跨容器转移。
- 装备/卸下武器。
- 单位移动与 Grid Occupancy 更新。
- Session Snapshot 恢复。
- 成功撤离到基地仓库的物品移交。

# 20. 兼容迁移策略

## 20.1 总体原则

- 不一次性重写所有系统。
- 每个阶段保持项目可运行。
- 提供兼容代理，再迁移调用者，最后删除旧字段。
- 不修改当前地图布局作为自动迁移副作用。
- 不让新 Snapshot 依赖旧 Node 实例身份。

## 20.2 Item 迁移

1. 增加统一 ID Generator 和 Item Factory。
2. `InventoryItemInstance` 接入 Definition Key。
3. 新增 Snapshot。
4. LootContainer 和 Inventory 改用 Factory。
5. Placement rotation 成为权威。
6. UI 改为读取 Placement rotation。
7. 废弃 Instance rotation 和 `copy()` 旧语义。

## 20.3 Unit 迁移

1. 增加 `UnitRuntimeState`。
2. `PrototypeUnit.configure()` 内部创建或绑定 State。
3. HP/AP/Cell/Facing 属性先代理到 State。
4. Controller 改为通过 State 执行规则。
5. Grid Occupancy 使用稳定 Unit Instance ID。
6. Snapshot 能在无 Unit Node 时恢复。
7. Node 销毁重建测试通过后，移除重复字段。

## 20.4 Weapon 迁移

1. 增加最小 `WeaponInstance`。
2. Unit Factory 根据 Spawn 的 WeaponDefinition 创建实例。
3. Unit Runtime 保存 weapon instance ID。
4. `PrototypeUnit.weapon` 暂时代理 `weapon_instance.definition`。
5. 后续弹药、耐久、配件只进入 Weapon Instance。

## 20.5 Map/Environment 迁移

1. 保留现有 MapDefinition 和 Marker 数据。
2. 为 Map Placement 增加稳定 placement ID 约束。
3. 战局创建时生成 Environment State。
4. 地图对象 Node 改为 View。
5. 后续环境交互系统只修改 State 和动态 Grid Overlay。

# 23. 测试策略

## 23.1 自动化测试原则

测试只验证功能合同，使用内存构造的最小 Definition、Runtime State 和 Snapshot。

遵循项目要求：

> 不为正式地图或持续编辑的地图内容编写位置、尺寸和布局断言。

## 23.2 Definition/Registry 测试

- 不同类型允许使用相同裸 ID，但 Definition Key 不冲突。
- 同类型重复 ID 被拒绝。
- 无效 Definition 被报告。
- 缺失 Definition 恢复失败并返回稳定原因码。
- Alias 能迁移旧 ID。
- Alias 循环被拒绝。

## 23.3 Instance/ID 测试

- 同一 Definition 创建两个实例，ID 不同。
- 修改实例 A 不影响实例 B。
- 修改实例不改变 Definition。
- 重复实例 ID 无法注册。
- 给定相同 Session ID 和创建顺序，测试生成结果确定。
- 恢复生成器计数后不会重复分配旧 ID。

## 23.4 Item/Inventory/Loot 测试

- 跨容器转移保持同一实例 ID。
- 转移失败不会复制或丢失物品。
- 一个实例不能同时被两个容器拥有。
- Placement rotation 是唯一权威来源。
- Snapshot 往返保持占格、旋转、价值和身份。
- LootSettlement 不丢失个体状态。

## 23.5 Unit/Weapon 测试

- Unit State 在没有 Node 时可以伤害、消耗 AP 和移动。
- 两个同 Archetype 单位状态互不影响。
- View 重建后显示状态一致。
- 两把同 Definition 武器具有不同实例 ID。
- 装备转移保持武器身份。
- Definition 基础数值没有被运行时修改。

## 23.6 Session/Snapshot 测试

- Snapshot → Codec → Decode → Restore 语义一致。
- Unsupported schema 被明确拒绝。
- Hydration 不触发死亡、奖励或 Loot 副作用。
- 恢复后 Registry 中无重复 ID。
- 所有 Item Instance 恰好具有一个 Owner/Location。
- Grid Occupancy 可由 Unit State 重建。

## 23.7 明确不编写的测试

- 某张地图必须有固定地格数量。
- 某坐标必须存在固定对象。
- 某正式地图必须生成固定数量敌人或 Loot。
- 因地编或美术调整就需要修改的场景快照测试。

地图内容使用地编 Validator 和人工验收；运行时系统使用合成数据测试。

# 26. 风险与控制措施

| 风险 | 控制措施 |
| --- | --- |
| 一次性重构导致 Demo 无法运行 | 分阶段兼容迁移，每阶段保持可运行 |
| Definition 在运行时被误改 | 只读约定、测试和代码审查；运行状态只写 Instance |
| 新旧状态字段同时存在并产生分叉 | 明确权威来源；兼容字段只做代理并安排删除阶段 |
| ID 生成器与现有局部 ID 冲突 | 统一 Generator；Registry 拒绝重复；保存计数器状态 |
| Snapshot 保存 Resource/Node 导致无法恢复 | Codec 只接受基础值和 Snapshot DTO |
| Definition 改名破坏旧存档 | Alias/Migrator；禁止静默改稳定 ID |
| Unit View 与 State 双向修改循环 | Command 改 State，View 单向订阅；绑定期间防重复事件 |
| 恢复时触发死亡和奖励 | 静默 Hydration，完成后一次性发布恢复完成事件 |
| 过度抽象拖慢玩法 | 公共基类保持极薄；只实现当前真实状态字段 |
| Runtime Registry 变成万能对象 | Registry 只索引和校验；领域容器继续拥有具体状态 |
| 正式地图调整导致测试频繁失败 | 测试使用合成数据；地图内容交给 Validator/人工验收 |
| 两个开发会话修改同一文件 | 明确文件所有权，共享接口由会话 A 独占 |

# 27. 最终架构判断

当前项目不需要推翻现有数据结构。

正确方向是：

```text
保留现有 Definition
→ 补统一 Definition Key 和 Registry
→ 统一实例 ID
→ 收口 Item/Placement/Loot
→ 把 Unit State 从 Node 中分离
→ 建立 Weapon Instance
→ 聚合 RaidSessionState 和 Snapshot
→ 为环境对象建立 Runtime State
→ 再开发爆炸、推动和地形杀
```

最终需要达到的状态是：

> Definition 是可复用、可编辑的内容模板；Runtime Instance 是独立、可查询、可保存的具体对象；Placement 只描述位置和所有权；Node 和 UI 始终是运行时权威状态的表现。

这套基础完成后，Loot、撤离结算、基地仓库、单位持久化、武器耐久、环境破坏和随机地图元素可以在同一身份与快照体系上继续扩展，而不需要分别建立互不兼容的临时状态方案。

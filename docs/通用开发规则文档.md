# 通用开发规则文档

| **文档版本** | V1.0 |
| --- | --- |
| **适用范围** | 项目全部系统开发阶段 |
| **文档用途** | 统一系统设计、功能开发、内容扩展、代码维护与验收时的基本原则 |
| **核心目标** | 保证项目能够在持续增加内容的情况下保持系统可扩展、可维护、可调试 |

---

# 1. 文档目的

本项目后续会持续增加：

- 武器。
- 敌人。
- Loot。
- 环境对象。
- 芯片。
- 技能。
- 地图内容。
- 撤离方式。
- 基地设施。

因此开发过程中不能只考虑：

> “当前这个功能能不能跑起来。”

还需要同时考虑：

> “后续增加同类型内容时，是否能够在现有基础上继续扩展。”

本文件只定义通用开发原则。

具体系统采用何种类结构、数据结构、资源类型和代码实现，由对应技术设计和实际开发决定。

---

# 2. 框架优先

开发一个新的系统时，应优先建立能够承载后续同类内容的基础能力。

例如：

开发武器时，不应只实现：

- 步枪。
- 霰弹枪。

而应优先保证：

- 武器可以配置基础属性。
- 武器可以具有不同攻击距离。
- 武器可以具有不同攻击方式。
- 武器可以继续增加特殊效果。

随后再使用少量实际武器验证系统。

原则：

> **先建立系统，再增加内容。**

---

# 3. 内容与系统分离

应明确区分：

## 系统

决定规则如何运行。

例如：

- 武器攻击。
- 掩体判定。
- 感知。
- 爆炸。
- Loot。
- 背包。

## 内容

使用系统产生的具体游戏对象。

例如：

- 步枪。
- 霰弹枪。
- 爆炸桶。
- 木箱。
- 某一种敌人。
- 某一个芯片。

开发具体内容时，应尽量使用已有系统，而不是为每个内容重新建立一套规则。

---

# 4. 数据驱动优先

能够通过配置表达的差异，应优先通过数据配置，而不是写死在逻辑代码中。

例如武器之间的差异：

- 伤害。
- 射程。
- AP。
- 距离衰减。
- 图标。
- 攻击范围。

应尽量作为数据配置。

不推荐在核心逻辑中大量出现：

```
如果武器是 A：
    ...
如果武器是 B：
    ...
如果武器是 C：
    ...
```

除非该内容确实具有无法复用的特殊规则。

---

# 5. 能力组合优先

复杂对象应尽量通过多个基础能力组合形成。

例如：

## 门

可能由以下能力组合：

- 可交互。
- 阻挡通行。
- 阻挡 LOS。
- 状态切换。

## 爆炸桶

可能由：

- 可破坏。
- 爆炸。
- 可推动。

## 未来发电机

可能由：

- 可交互。
- 可破坏。
- 供电。

原则：

> **优先复用基础能力，再考虑新增专用系统。**

---

# 6. 避免过度设计

框架优先不等于一次设计未来所有可能出现的功能。

只需要为已经明确的变化方向提供扩展空间。

例如当前已经明确武器可能具有：

- 不同攻击距离。
- 不同攻击范围。
- Push。
- 穿甲。
- 环境破坏。

这些属于合理扩展方向。

但尚未进入策划范围的：

- 枪械过热。
- 卡弹。
- 风偏。
- 复杂弹道模拟。

不应为了“以后可能用到”而提前实现。

原则：

> **为已知变化设计，为未知变化保留修改空间。**

---

# 7. 单一规则来源

同一个游戏规则应尽量只存在一套正式计算逻辑。

例如：

“这个目标是否处于掩体保护下？”

不应分别由：

- 玩家攻击系统。
- AI。
- UI。

各自计算一遍。

更合理的是：

三者都获取同一个规则结果。

这样可以避免：

- UI 显示可以攻击，但实际不能攻击。
- AI 认为有掩体，但玩家系统认为没有。
- 修改一处规则后另一处没有同步。

原则：

> **同一规则，只维护一个权威结果。**

---

# 8. 表现层不负责决定规则

UI、动画、特效等表现层主要负责：

- 展示结果。
- 提供反馈。
- 接收操作。

不应成为核心规则的最终决定者。

例如：

爆炸范围应先由游戏规则确定。

然后 UI 和特效再根据结果显示：

- 高亮哪些格。
- 播放哪些特效。
- 显示哪些伤害。

而不是让特效范围反过来决定谁受到伤害。

---

# 9. 系统之间保持清晰职责

每个系统应尽量回答一个明确的问题。

例如：

- Grid：位置和格子关系。
- LOS：两个位置之间是否存在视线。
- Visibility：玩家当前能看到哪些区域。
- Cover：单位当前是否受到掩体保护。
- Weapon：武器允许执行什么攻击。
- AI：敌人在当前状态下决定做什么。

避免一个大型系统同时负责：

- 地图。
- 战斗。
- AI。
- UI。
- Loot。

职责越混乱，后续扩展成本越高。

---

# 10. 不为具体内容污染核心流程

新增一个具体内容时，应首先判断：

> “这是已有规则的新组合，还是确实出现了新的通用规则？”

例如新增：

**爆炸霰弹枪**

如果已经存在：

- 武器。
- 范围效果。
- 爆炸。

则优先组合已有能力。

不应立刻新增：

```
ExplosionShotgunSpecialSystem
```

除非现有系统确实无法合理表达需求。

---

# 11. 新增内容时优先扩展配置

后续内容扩展的理想开发流程：

**创建新内容**

↓

**配置已有参数**

↓

**选择已有能力**

↓

**组合效果**

↓

**测试**

只有现有能力无法表达策划需求时，才增加新的底层能力。

---

# 12. 保持系统可替换和可修改

系统设计不应假设当前玩法永远不会改变。

例如当前：

- 每回合 2 AP。
- 武器攻击消耗 1 AP。

后续可能出现：

- 击杀返还 AP。
- 第一次攻击免费。
- 某技能攻击消耗 2 AP。

因此基础系统应避免把：

```
攻击永远消耗 1 AP
```

作为不可修改的固定逻辑。

但也不需要一开始实现全部未来规则。

只需要避免明显锁死。

---

# 13. 优先使用通用状态，而不是大量布尔值

随着系统复杂度增加，应避免出现大量互相冲突的状态变量。

例如：

```
is_alert
is_suspicious
is_combat
is_patrolling
```

如果这些状态互斥，更适合统一表达成明确状态。

例如：

```
未警戒
怀疑
交战
```

原则：

> **互斥状态优先使用统一状态表达。**

---

# 14. 状态变化必须同步影响规则

如果一个对象状态变化会影响其他系统，需要保证变化结果能够正确传播。

例如门：

**关闭 → 开启**

必须同步影响：

- 寻路。
- LOS。
- 战争迷雾。
- UI。

可破坏墙体：

**完整 → 已破坏**

可能同步影响：

- 通行。
- 掩体。
- LOS。
- 可见性。

不能只更新模型表现。

---

# 15. 运行时状态与静态配置分离

应尽量区分：

## 静态配置

描述“一类对象是什么”。

例如：

- 武器基础伤害。
- 最大射程。
- 物品形状。
- 爆炸半径。

## 运行时状态

描述“这一件对象现在怎么样”。

例如：

- 当前耐久。
- 当前弹药。
- 当前所在格。
- 当前是否打开。
- 当前警戒状态。

避免直接修改公共配置数据来保存运行时状态。

---

# 16. 新系统必须考虑存档与重建

即使当前 Demo 尚未完整实现存档，新系统也应尽量保证关键状态可以被描述和恢复。

例如：

- 单位所在格。
- 门的状态。
- 物品实例。
- 当前 HP。
- 当前装备。

避免关键状态只存在于动画、临时节点或无法恢复的表现对象中。

---

# 17. AI 与玩家尽量复用规则

如果玩家和 AI 遵守相同的战斗规则，应尽量复用同一套基础能力。

例如：

- 寻路。
- 攻击范围。
- 掩体。
- LOS。
- 武器距离。

AI 应根据这些规则“做决策”，而不是自己复制一套规则。

---

# 18. UI 与规则保持一致

UI 中的预览应尽量来自实际规则计算。

例如：

- 可移动格。
- 可攻击目标。
- 伤害预览。
- 掩体。
- 侧翼。
- 爆炸范围。

避免 UI 使用一套估算，而执行阶段使用另一套算法。

---

# 19. 优先保证规则可预测

当前项目核心强调战术决策。

因此在核心系统尚未稳定前，应谨慎增加大量随机结果。

例如：

P1 阶段优先使用：

- 确定性伤害。
- 确定性移动。
- 确定性掩体效果。

而不是立即增加：

- 大量随机命中。
- 随机暴击。
- 无规律 AI。

玩家应该能够理解：

> “为什么这次行动产生这个结果。”

---

# 20. 每个系统必须有最低验证内容

框架完成后必须通过具体内容验证。

例如：

## 武器系统

至少：

- 步枪。
- 霰弹枪。

## 掩体系统

至少：

- 半掩体。
- 全掩体。

## 环境交互

至少：

- 门。

## 可破坏系统

至少：

- 一个可破坏环境对象。

不能只写接口但没有实际游戏内容验证。

---

# 21. 每个系统必须考虑扩展性验证

除了确认“当前内容能运行”，还应测试：

> “能不能方便地增加第二个、第三个同类内容？”

例如：

完成步枪和霰弹枪后，尝试增加 DMR。

如果新增 DMR 需要：

- 大量修改攻击流程。
- 大量添加专用判断。
- 修改多个不相关系统。

说明武器系统扩展性不足。

扩展性测试本身属于系统验收的一部分。

---

# 22. 避免过早制作大量内容

系统尚未稳定时，不建议立即制作：

- 十几把武器。
- 十几种敌人。
- 大量地图。
- 大量 Loot。

推荐：

**系统 → 1～2 个内容 → 测试 → 调整 → 再增加内容**

否则系统修改后会产生大量内容返工。

---

# 23. 先解决通用问题，再解决特殊问题

如果多个功能都出现相同需求，应优先提炼成通用能力。

例如：

- 霰弹枪需要 Push。
- 爆炸需要 Push。
- 技能也可能需要 Push。

则应优先考虑统一的强制位移能力。

而不是：

- ShotgunPush。
- ExplosionPush。
- SkillPush。

各写一套。

---

# 24. 保持 Debug 能力

复杂系统必须具备基本调试手段。

尤其是：

- Grid。
- LOS。
- Visibility。
- AI 状态。
- 掩体。
- 攻击范围。
- 路径。
- 环境状态。

如果规则不可见，出现问题后开发成本会快速上升。

原则：

> **无法观察的系统很难维护。**

---

# 25. 开发顺序优先保证依赖稳定

开发新功能时，应优先完成被多个系统依赖的基础能力。

例如：

Grid

↓

LOS

↓

Visibility

↓

战争迷雾

而不是先写大量依赖 Visibility 的特殊内容。

开发顺序应尽量减少重复返工。

---

# 26. 系统开发完成定义

一个系统不能只以：

> “功能能够运行。”

作为完成标准。

至少需要同时满足：

1. 核心功能可用。
2. 与已有系统正确联动。
3. 有实际内容进行验证。
4. 有基本 UI / Debug 能够观察结果。
5. 边界情况不会明显破坏流程。
6. 可以方便增加至少一种新的同类内容。

---

# 27. 需求与技术实现分离

需求文档负责：

- 为什么做。
- 要实现什么。
- 当前做到什么程度。
- 什么结果算完成。

技术设计负责：

- 类结构。
- Resource 设计。
- Node 设计。
- 接口。
- Signal / Event。
- 文件目录。
- 数据流。
- 具体算法。

需求文档不应强制规定尚未验证的技术实现。

同样，技术实现不能擅自改变需求目标。

---

# 28. 优先保持简单

如果一个简单方案能够满足：

- 当前需求。
- 已知扩展方向。
- 基本维护要求。

则优先使用简单方案。

不要为了所谓“通用性”构建远超项目当前规模的复杂架构。

原则：

> **足够扩展，而不是无限抽象。**

---

# 29. 定期重构允许存在

系统第一次实现不要求永远正确。

随着：

- 新玩法增加。
- 需求明确。
- 重复逻辑出现。

允许进行重构。

但重构应该：

- 有明确问题。
- 有明确收益。
- 不为了追求形式上的完美架构。

---

# 30. 项目统一原则总结

所有系统开发优先遵循以下原则：

1. **框架优先，内容验证。**
2. **系统与内容分离。**
3. **数据驱动优先。**
4. **能力组合优先。**
5. **为已知变化设计，不为未知需求过度设计。**
6. **同一规则保持单一权威来源。**
7. **AI、UI、玩家行为尽量复用相同规则。**
8. **表现层不决定核心规则。**
9. **状态变化必须同步影响相关系统。**
10. **静态配置与运行时状态分离。**
11. **系统必须可观察、可调试。**
12. **先少量内容验证，再批量生产。**
13. **系统完成必须包含扩展性验证。**
14. **需求描述目标，技术文档描述实现。**
15. **保持简单，允许后续重构。**

---

# 31. 最终目标

本规则的目的不是追求一个“最通用的游戏框架”。

真正目标是：

> **让项目在不断增加武器、敌人、Loot、环境、Build 和局外内容的过程中，不需要不断推翻已有系统。**

系统应该随着游戏一起成长。

每一次新增内容都应优先成为：

**已有能力的新配置或新组合**

只有真正出现新的通用玩法规则时，才继续扩展底层系统。
